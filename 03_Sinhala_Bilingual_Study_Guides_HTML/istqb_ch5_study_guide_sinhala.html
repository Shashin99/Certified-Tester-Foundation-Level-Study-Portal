1. Core Syllabus Concepts & In-Depth Notes (මූලික විෂය කරුණු)

5.1 Test Planning (පරීක්ෂණ සැලසුම්කරණය) FL-5.1.1 FL-5.1.2 FL-5.1.3

නිල අර්ථ දැක්වීම (Formal Definition): A Test Plan describes the test objectives, resources, and processes for a test project. It guides testers' thinking, forces confrontation with future challenges (risks, schedules, costs), and serves as a vehicle of communication with stakeholders.
(පරීක්ෂණ සැලැස්මක් මඟින් ව්‍යාපෘතියක පරීක්ෂණ අරමුණු, ඒ සඳහා අවශ්‍ය සම්පත් සහ ක්‍රියාවලිය පැහැදිලි කරයි. එමඟින් අනාගතයේ මුහුණ දීමට සිදුවන අවදානම් (risks), කාලසටහන් (schedules) සහ පිරිවැය (costs) කල්තියා හඳුනා ගැනීමටත් පාර්ශ්වකරුවන් සමඟ නිසි සන්නිවේදනයක් පවත්වා ගැනීමටත් උපකාරී වේ.)

5.1.1 Purpose and Typical Content of a Test Plan (ISO/IEC/IEEE 29119-3)

පරීක්ෂණ සැලසුම්කරණයේ ප්‍රධාන අරමුණු (Core Purposes):
  • පරීක්ෂණ අරමුණු සපුරා ගැනීමේ ක්‍රමවේදය සහ කාලසටහන ලේඛනගත කිරීම.
  • සිදුකරන ක්‍රියාකාරකම් ස්ථාපිත නිර්ණායක (criteria) සමඟ සැසඳෙන බව තහවුරු කිරීම.
  • කණ්ඩායම සහ ව්‍යාපෘති පාර්ශ්වකරුවන් (stakeholders) අතර සන්නිවේදන මාධ්‍යයක් ලෙස ක්‍රියා කිරීම.
  • ආයතනික පරීක්ෂණ ප්‍රතිපත්තියට (Test Policy) සහ උපාය මාර්ගයට (Test Strategy) අනුකූල බව පෙන්වීම (නොඑසේ නම් වෙනස්කම් සාධාරණීකරණය කිරීම).
පරීක්ෂණ සැලැස්මක අඩංගු ප්‍රධාන කොටස් (Typical Sections):
  • Context: Test scope (පරිමාව), objectives (අරමුණු), සහ test basis.
  • Assumptions & Constraints: පූර්ව නිගමන සහ සීමාවන් (budget, deadlines).
  • Stakeholders: වගකීම් (roles), පුහුණු කිරීම් සහ බඳවා ගැනීමේ අවශ්‍යතා.
  • Risk Register: හඳුනාගත් Product සහ Project risks ලේඛනය.
  • Test Approach: Test levels, types, techniques, criteria සහ tools.
  • Budget & Schedule: වැයවන මුදල, සන්ධිස්ථාන (milestones) සහ කාලසටහන.

5.1.2 Tester's Contribution to Iteration and Release Planning FL-5.1.2 (K1)

Release Planning (දීර්ඝකාලීන සැලසුම්කරණය):

නිෂ්පාදනයක් නිකුත් කිරීම (Release) දක්වා ඇති දීර්ඝකාලීන පියවර සැලසුම් කරයි. මෙහිදී Product Backlog එක පිරිපහදු කර විශාල කතාන්දර (Epics) කුඩා User Stories වලට කඩයි. ටෙස්ටර්ගේ දායකත්වය:
• පරීක්ෂා කළ හැකි (Testable) User Stories සහ Acceptance Criteria ලිවීම.
• Project සහ Quality Risk Analysis සඳහා සහභාගී වීම.
• User Stories සඳහා වැයවන පරිශ්‍රමය (Testing Effort) ඇස්තමේන්තු කිරීම.
• සියලු Iterations හරහා ගමන් කරන පොදු පරීක්ෂණ ප්‍රවේශය (Overall Test Approach) අර්ථ දැක්වීම.

Iteration Planning (Sprint සැලසුම්කරණය):

තනි කෙටිකාලීන Iteration එකක් (Sprint) ඉලක්ක කරගෙන සිදුකරන සැලසුම්කරණයයි. ටෙස්ටර්ගේ දායකත්වය:
• තනි තනි User Stories වල සවිස්තරාත්මක අවදානම් විශ්ලේෂණය (Detailed Risk Analysis).
• User Stories වල පරීක්ෂා කිරීමේ හැකියාව (Testability) තක්සේරු කිරීම.
• User Stories පරීක්ෂණ කාර්යයන් (Testing Tasks) වලට වෙන් කිරීම.
• එක් එක් කාර්යය සඳහා අවශ්‍ය කාලය හා පරිශ්‍රමය ඇස්තමේන්තු කිරීම.
• Functional සහ Non-functional අවශ්‍යතා නිශ්චිතව හඳුනා ගැනීම.

5.1.3 Entry Criteria and Exit Criteria FL-5.1.3 (K2)

පරාමිතිය (Dimension) Entry Criteria (Definition of Ready - DoR) Exit Criteria (Definition of Done - DoD)
මූලික අරමුණ (Formal Purpose) යම් පරීක්ෂණ ක්‍රියාකාරකමක් ආරම්භ කිරීමට සපුරාලිය යුතු පූර්ව අවශ්‍යතා (Preconditions) වේ. මේවා නොමැතිව පරීක්ෂාව ඇරඹීම අධික අවදානමකි. යම් ක්‍රියාකාරකමක්, පරීක්ෂණ මට්ටමක් හෝ Release එකක් අවසන් කළ බව (Completed) නිල වශයෙන් ප්‍රකාශ කිරීමට සපුරාලිය යුතු කොන්දේසි වේ.
සාමාන්‍ය උදාහරණ (Typical Examples) • Testware සූදානම් වීම (පැහැදිලි requirements, test cases)
• Test Environment, Data, Tools සහ Staff ලබාගත හැකි වීම
• මූලික Smoke Tests සාර්ථකව සමත් වීම 		• ආවරණය සපුරා ගැනීම (Achieved coverage, e.g. 100% statement)
• විසඳා නොමැති බරපතල දෝෂ නොමැති වීම (Zero critical defects)
• සියලු Regression tests ස්වයංක්‍රීයව ක්‍රියාත්මක වීම
අයවැය / කාල සීමා යථාර්ථය (Budget & Schedule Reality) අසම්පූර්ණ හෝ බිඳවැටුණු build එකක් පරීක්ෂා කිරීමට වඩා Entry criteria සපුරන තෙක් ප්‍රමාද කිරීම වඩාත් සුදුසුය. කාලය හෝ මුදල් අවසන් වීමද Exit Criterion එකක් විය හැකිය — එහෙත් ඒ සඳහා ඉතිරිව ඇති අවදානම (Residual Risk) පාර්ශ්වකරුවන් විසින් පිළිගත යුතුය!

5.1.4 Test Effort Estimation Techniques (පරීක්ෂණ පරිශ්‍රමය ඇස්තමේන්තු කිරීමේ ශිල්පක්‍රම) FL-5.1.4 (K3)

පරීක්ෂණ අරමුණු සපුරා ගැනීම සඳහා වැයවන වැඩ කොටස (Effort) කල්තියා ගණනය කිරීම මෙහිදී සිදුකෙරේ. විශාල කාර්යයන් කුඩා කොටස්වලට කඩා (Decomposition) ඇස්තමේන්තු කිරීම ඉතා නිවැරදි ප්‍රතිඵල ලබා දෙයි.

1. Estimation Based on Ratios (අනුපාත මත පදනම් වූ - Metrics-Based):

ආයතනයේ පෙර ව්‍යාපෘතිවල දත්ත රැස්කර සම්මත අනුපාතයක් නිර්මාණය කරගැනීම.
ගණනය කිරීමේ උදාහරණය: Development සහ Testing අතර අතීත අනුපාතය 3 : 2 නම්, නව ව්‍යාපෘතියේ Dev effort එක දින 600 ක් ලෙස තක්සේරු කර ඇත්නම්:
Test Effort = 600 × (2 / 3) = දින 400 (Person-days)

2. Extrapolation (බාහිර නිස්සාරණය - Metrics-Based):

වත්මන් ව්‍යාපෘතියේ ආරම්භක අදියරවලින් රැස්කරගත් මිනුම් අනාගතය සඳහා ගණිතමය වශයෙන් දිගු කිරීම. Agile/Iterative ක්‍රමවේද සඳහා වඩාත් යෝග්‍ය වේ.
ගණනය කිරීමේ උදාහරණය: Sprint 1, 2, 3 සඳහා සැබෑ පරීක්ෂණ කාලය දින 18, 22, 20 ක් වූයේ නම්, Sprint 4 හි සාමාන්‍යය:
Sprint 4 Effort = (18 + 22 + 20) / 3 = දින 20 (Person-days)

3. Wideband Delphi (විශේෂඥ එකඟතා ක්‍රමය - Expert-Based):

විශේෂඥයින් කිහිපදෙනෙකු වෙන් වෙන්ව ස්වාධීනව ඇස්තමේන්තු ඉදිරිපත් කරයි. එම ඇස්තමේන්තු සසඳා බලා වෙනස්කම් සාකච්ඡා කර, එකඟතාවයක් (Consensus) ලැබෙන තෙක් නැවත නැවත රහසිගතව ඇස්තමේන්තු සකස් කරයි.
• Planning Poker: Story points කාඩ්පත් භාවිතයෙන් සිදුකරන Agile ආකෘතියයි.

4. Three-Point Estimation / PERT (Expert-Based):

විශේෂඥයින් විසින් ඇස්තමේන්තු තුනක් ලබා දෙයි:
• a = Most optimistic (වඩාත්ම සුබවාදී / අවම කාලය)
• m = Most likely (වඩාත්ම ඉඩකඩ ඇති කාලය)
• b = Most pessimistic (වඩාත්ම අසුබවාදී / උපරිම කාලය)
භාරිත සාමාන්‍යය (E) සහ සම්මත අපගමනය (SD):

E = (a + 4m + b) / 6    |    SD = (b − a) / 6

විභාග ගණනය කිරීමේ උදාහරණය: Three-Point Estimation Calculation

ගැටලුව: ගෙවීම් පද්ධතියක් පරීක්ෂා කිරීමට විශේෂඥයින් තක්සේරු කරන්නේ: Optimistic a = පැය 6, Most likely m = පැය 9, Pessimistic b = පැය 18.
පියවර 1 (භාරිත ඇස්තමේන්තුව E ගණනය කිරීම):
  • E = (6 + 4(9) + 18) / 6 = (6 + 36 + 18) / 6 = 60 / 6 = පැය 10 (Person-hours)
පියවර 2 (මිනුම් දෝෂය / සම්මත අපගමනය SD ගණනය කිරීම):
  • SD = (18 − 6) / 6 = 12 / 6 = පැය 2 (Person-hours)
අවසාන වාර්තාගත ඇස්තමේන්තුව: පැය 10 ± 2 (විශ්වාසනීය පරාසය: පැය 8 ත් 12 ත් අතර).

5.1.5 Test Case Prioritization (පරීක්ෂණ අවස්ථා ප්‍රමුඛතාකරණය) FL-5.1.5 (K3)

Test cases සහ procedures එකතු කර Test Suites සාදන විට, ඒවා ධාවනය කරන අනුපිළිවෙල (Execution Schedule) තීරණය කිරීමට ප්‍රධාන ප්‍රවේශ තුනක් භාවිත කරයි:

ප්‍රමුඛතාකරණ උපායමාර්ගය (Strategy) අනුපිළිවෙල තීරණය කරන යාන්ත්‍රණය (Ordering Mechanism) ප්‍රායෝගික යෙදවුම (Application)
Risk-Based Prioritization නිෂ්පාදන අවදානම (Product Risk) මූලික වේ. ඉහළම අවදානම් සහිත Test cases පළමුව ධාවනය කරයි. ආරක්ෂක (Security) සහ ගෙවීම් පද්ධති පරීක්ෂාව පළමු දිනයේම සිදුකිරීම.
Coverage-Based Prioritization කේත හෝ අවශ්‍යතා ආවරණය (Coverage) මත තීරණය වේ. Additional Coverage Prioritization හිදී උපරිම ආවරණයක් ලබාදෙන test cases මුලින්ම run කරයි. සීමිත කාලයක් තුළ උපරිම කේත ආවරණයක් තහවුරු කිරීමට අවශ්‍ය වූ විට.
Requirements-Based Prioritization පාර්ශ්වකරුවන් විසින් අදාළ අවශ්‍යතාවලට ලබාදී ඇති ව්‍යාපාරික වැදගත්කම (Business Priority) මත පදනම් වේ. MoSCoW ක්‍රමය අනුව "Must-Have" අවශ්‍යතා මුලින්ම පරීක්ෂා කිරීම.
අතිශය තීරණාත්මක විභාග රීතිය: Test Dependencies & Resource Constraints:
යම් Test Case එකක් ඉහළම ප්‍රමුඛතාවක් සහිත එකක් වුවද, එය ක්‍රියාත්මක වීමට අඩු ප්‍රමුඛතාවක් ඇති වෙනත් Test Case එකක් මත තාක්ෂණිකව රඳා පවතින්නේ නම් (Dependency), අනිවාර්යයෙන්ම අඩු ප්‍රමුඛතා Test Case එක පළමුව ධාවනය කළ යුතුය! (උදා: Login හෝ Data create කිරීමේ test එක මුලින්ම run විය යුතුය).

5.1.6 The Test Pyramid (පරීක්ෂණ පිරමිඩය) FL-5.1.6 (K1)

මූලික සංකල්පය (Mike Cohn): පරීක්ෂණ පිරමිඩය මඟින් විවිධ පරීක්ෂණ මට්ටම්වල පවතින විභේදනය (granularity), හුදකලා බව (isolation) සහ ස්වයංක්‍රීයකරණයේ ප්‍රමාණය නිරූපණය කරයි.
THE TEST PYRAMID LAYERS
Level 3 (Top): UI & End-to-End Tests (ස්වල්පයයි, සංකීර්ණයි, සෙමෙන් ධාවනය වේ, Low Isolation)
Level 2 (Middle): Service & Integration Tests (මධ්‍යස්ථ වේගය සහ හුදකලා බව)
Level 1 (Base): Unit & Component Tests (ඉතා විශාල සංඛ්‍යාවක්, කුඩායි, ක්ෂණිකයි, High Isolation)

පිරමිඩයේ ප්‍රධාන රීති (Syllabus Rules):

  • Bottom Layer (Unit): පරීක්ෂණ කුඩාය, ඉතා හුදකලාය (isolated), ඉතා වේගවත්ය. ප්‍රමාණවත් ආවරණයක් සඳහා විශාල පරීක්ෂණ ගණනක් අවශ්‍ය වේ.
  • Top Layer (UI / E2E): පද්ධතියම එකවර පරීක්ෂා කරන සංකීර්ණ පරීක්ෂණ වේ. සෙමෙන් ධාවනය වන අතර, අවශ්‍ය වන්නේ සුළු සංඛ්‍යාවකි.
  • විභාග රීතිය: පිරමිඩයේ ඉහළට යත්ම, Granularity අඩු වේ, Isolation අඩු වේ (අනෙක් කොටස් මත යැපීම වැඩි වේ), සහ Execution Time එක වැඩි වේ!

5.1.7 The Testing Quadrants (පරීක්ෂණ චතුර්ථක) FL-5.1.7 (K2)

මූලික අරමුණ (Brian Marick): Agile ක්‍රමවේද තුළ පරීක්ෂණ මට්ටම්, වර්ග සහ ශිල්පක්‍රම එකමුතු කර නිසි ආවරණයක් ලබාගැනීමටත්, තාක්ෂණික හා ව්‍යාපාරික සාමාජිකයන් අතර සන්නිවේදනය පහසු කිරීමටත් මෙම ආකෘතිය උපකාරී වේ.

මෙම ආකෘතිය ප්‍රධාන අක්ෂ දෙකක් ඔස්සේ බෙදා ඇත: (1) Business Facing vs. Technology Facing, සහ (2) Supporting the Team (කණ්ඩායමට මඟ පෙන්වීම) vs. Critiquing the Product (නිෂ්පාදනය විවේචනාත්මකව ඇගයීම):

Quadrant Q1: Technology Facing • Support Team

• පරීක්ෂණ වර්ග: Component testing (unit) සහ Component integration testing.
• ස්වභාවය: ඉතා ඉහළ ස්වයංක්‍රීයකරණයක් සහිතයි; CI/CD pipeline තුළට සෘජුවම බද්ධ කර ඇත.
• ඉලක්කය: කේතයේ මූලික නිරවද්‍යතාව තහවුරු කරමින් සංවර්ධකයාට මඟ පෙන්වීම.

Quadrant Q2: Business Facing • Support Team

• පරීක්ෂණ වර්ග: Functional tests, User story tests, API testing, UX prototypes, Simulations.
• ස්වභාවය: User stories වල acceptance criteria සනාථ කරයි; Manual හෝ Automated විය හැක.
• ඉලක්කය: ව්‍යාපාරික අවශ්‍යතාවලට ගැලපෙන ලෙස මෘදුකාංගය තැනීමට උපකාරී වීම.

Quadrant Q3: Business Facing • Critique Product

• පරීක්ෂණ වර්ග: Exploratory testing, Usability testing, User Acceptance Testing (UAT).
• ස්වභාවය: සැබෑ පරිශීලකයාගේ ඇසින් බලන මානව ඇගයීමකි; ප්‍රධාන වශයෙන් Manual වේ.
• ඉලක්කය: පරිශීලක අත්දැකීම (UX) සහ ව්‍යාපාරික යෝග්‍යතාවය පරීක්ෂා කිරීම.

Quadrant Q4: Technology Facing • Critique Product

• පරීක්ෂණ වර්ග: Smoke tests සහ Non-functional tests (Performance, Load, Security, Reliability).
• සුවිශේෂී රීතිය: Usability පරීක්ෂාව Q3 හි පවතින අතර, අනෙකුත් සියලු non-functional පරීක්ෂණ අයත් වන්නේ Q4 වෙතයි!
• ස්වභාවය: මෙවලම් මඟින් මෙහෙයවන ස්වයංක්‍රීය පරීක්ෂණ (Tool-driven, Automated).

1.2 Risk Management (අවදානම් කළමනාකරණය)

නිල අර්ථ දැක්වීම (ISO 31000): A Risk is a potential event, hazard, threat, or situation whose occurrence causes an adverse effect. (අවදානමක් යනු අනාගතයේ සිදුවුවහොත් අහිතකර බලපෑමක් ඇතිකළ හැකි විභව සිදුවීමකි). අවදානම් විශ්ලේෂණය මත පදනම්ව පරීක්ෂණ සැලසුම් කිරීම Risk-Based Testing ලෙස හැඳින්වේ.

5.2.1 Risk Definition and Attributes FL-5.2.1 (K1)

අවදානමක් ප්‍රධාන සාධක දෙකකින් සමන්විත වේ:

  • Risk Likelihood: අවදානම සිදුවීමේ සම්භාවිතාව (0 < Likelihood < 1).
  • Risk Impact (Harm): එය සිදුවුවහොත් සිදුවන හානිය හෝ ප්‍රතිවිපාකය.
  • Risk Level: අවදානම් මට්ටම ගණනය කරනුයේ: Risk Level = Likelihood × Impact

5.2.2 Project Risks vs. Product Risks FL-5.2.2 (K2)

පරාමිතිය (Dimension) Project Risks (ව්‍යාපෘති අවදානම් - Management) Product Risks (නිෂ්පාදන අවදානම් - Quality)
මූලික අර්ථය ව්‍යාපෘතියේ කළමනාකරණයට සහ පාලනයට බලපාන අවදානම් (කාලසටහන, අයවැය, කාර්ය මණ්ඩලය). මෘදුකාංග නිෂ්පාදනයේ ගුණාත්මක ලක්ෂණවලට (Quality characteristics) බලපාන අවදානම්.
ආයතනික ගැටලු (Organizational) ලියකියවිලි ප්‍රමාද වීම, වැරදි ඇස්තමේන්තු, අයවැය කප්පාදු කිරීම්. දුර්වල මෘදුකාංග නිර්මාණ ශිල්පය (Architecture), නඩත්තු කිරීමට අපහසු වීම.
මානව සම්පත් (People Issues) කාර්ය මණ්ඩල හිඟය, කුසලතා ඌනතා, කණ්ඩායම් ගැටුම්, සන්නිවේදන බිඳවැටීම්. පරිශීලක අතෘප්තිය, දුර්වල පරිශීලක අත්දැකීම (Bad UX).
තාක්ෂණික ගැටලු (Technical Issues) Scope creep, ප්‍රමාණවත් test tools නොමැතිකම, test environment ප්‍රමාද වීම. ක්‍රියාකාරී දෝෂ (Functional bugs), System crashes, ආරක්ෂක සිදුරු (Vulnerabilities).
සැපයුම්කරුවන් (Supplier Issues) තෙවන පාර්ශ්ව ආයතනය බිඳවැටීම හෝ tool licenses ප්‍රමාද වීම. තෙවන පාර්ශ්ව API මඟින් දත්ත විකෘති වීම හෝ timeout වීම.
ප්‍රතිවිපාක (Consequences) මුදල් නාස්තිය, ව්‍යාපෘතිය අත්හැරීමට සිදුවීම, Deadlines මඟහැරීම. පාරිභෝගික මූල්‍ය පාඩු, නීතිමය ගැටලු, ජීවිත හෝ ශාරීරික හානි සිදුවීම.
විභාගයේදී වෙන්කර හඳුනාගැනීම (Exam Classification):
• "Test environment එක සති 3 කින් ප්‍රමාද විය" → Project Risk (කාලසටහනට තර්ජනයක්).
• "GPS භාවිතයේදී Mobile App එකෙන් Battery එක වේගයෙන් බැසයයි" → Product Risk (මෘදුකාංගයේ ගුණාත්මක අඩුපාඩුවක්).

5.2.3 Product Risk Analysis (නිෂ්පාදන අවදානම් විශ්ලේෂණය) FL-5.2.3 (K2)

මූලික අරමුණ: ඉතිරිවන අවදානම (Residual Risk) අවම කිරීම සඳහා පරීක්ෂණ කටයුතු නිසි ලෙස යොමු කිරීම. මෙහි උප-ක්‍රියාකාරකම් දෙකකි: Risk Identification (අවදානම් හඳුනාගැනීම) සහ Risk Assessment (අවදානම් තක්සේරු කිරීම).
1. Risk Identification:

Brainstorming සැසි, පාර්ශ්වකරුවන්ගේ සම්මුඛ සාකච්ඡා, checklists සහ අතීත අත්දැකීම් භාවිත කර ඇතිවිය හැකි සියලු අවදානම් ලැයිස්තුගත කිරීම.

2. Risk Assessment:

හඳුනාගත් අවදානම් වර්ගීකරණය කර, ඒවායේ Likelihood සහ Impact තක්සේරු කර Risk Level එක ගණනය කිරීම.
• Quantitative: සංඛ්‍යාත්මක අගයන් ගුණ කිරීම.
• Qualitative: Risk Matrix (High, Med, Low) භාවිතය.

Product Risk Analysis මඟින් පරීක්ෂණ ක්‍රියාවලිය මෙහෙයවන ආකාරය:

  • Test Scope තීරණය කිරීම: අධික අවදානම් සහිත කොටස් පුළුල් ලෙස පරීක්ෂා කරන අතර, අඩු අවදානම් කොටස් සඳහා සුළු පරීක්ෂාවක් සිදුකරයි.
  • Test Levels සහ Types තීරණය කිරීම: දැඩි ආරක්ෂක අවදානම් පවතී නම්, විශේෂිත Penetration testing සිදුකිරීමට තීරණය කිරීම.
  • Test Techniques තෝරාගැනීම: ඉහළ අවදානම් සඳහා 3-value BVA සහ Branch coverage භාවිත කරන අතර, සාමාන්‍ය අවදානම් සඳහා Exploratory testing භාවිතය.
  • ප්‍රමුඛතාව ලබාදීම (Prioritization): තීරණාත්මක දෝෂ කල්තියා හඳුනාගැනීම සඳහා ඉහළ අවදානම් පරීක්ෂණ පළමුව run කිරීම.

5.2.4 Product Risk Control (අවදානම් පාලනය) FL-5.2.4 (K2)

මූලික අරමුණ: තක්සේරු කළ අවදානම්වලට ප්‍රතිචාර දැක්වීම. මෙයට Risk Mitigation (අවදානම අවම කිරීමේ පියවර ගැනීම) සහ Risk Monitoring (පියවරවල සඵලතාවය පරීක්ෂා කිරීම හා නව අවදානම් නිරීක්ෂණය) අයත් වේ.

අවදානමකට ප්‍රතිචාර දැක්වීමේ මූලික විකල්ප 4 (Response Options):

1. Risk Mitigation

පරීක්ෂාව (Testing) හරහා අවදානම අවම කිරීමේ සෘජු ක්‍රියාමාර්ග ගැනීම.

2. Risk Acceptance

අවදානම හිතාමතාම පිළිගැනීම (හානිය අවම සුළු අවදානම් සඳහා).

3. Risk Transfer

තෙවන පාර්ශ්වයකට අවදානම පැවරීම (රක්ෂණාවරණ, Vendor contracts).

4. Contingency Plan

අවදානම සිදුවුවහොත් ක්‍රියාත්මක වීමට හදිසි සැලැස්මක් සකස් කර තැබීම.

1.3 Test Monitoring, Test Control and Test Completion

Test Monitoring (පරීක්ෂණ නිරීක්ෂණය):

පරීක්ෂණ ප්‍රගතිය පිළිබඳ දත්ත අඛණ්ඩව එක්රැස් කිරීම, සැලැස්මට (Test Plan) සාපේක්ෂව සත්‍ය තත්ත්වය ඇගයීම සහ Exit Criteria සපුරා ඇත්දැයි නිරීක්ෂණය කිරීම.

Test Control (පරීක්ෂණ පාලනය):

නිරීක්ෂණ දත්ත අනුව අපගමනයන් සිදුවී ඇත්නම්, පරීක්ෂණ අරමුණු සපුරා ගැනීම සඳහා ගන්නා නිවැරදි කිරීමේ පියවර (Corrective Actions / Directives) වේ (උදා: සම්පත් නැවත බෙදාහැරීම).

5.3.1 Metrics Used in Testing (පරීක්ෂාවේදී භාවිත වන මිනුම්) FL-5.3.1 (K1)

මිනුම් කාණ්ඩය (Category) නිශ්චිත උදාහරණ සහ අරමුණ (Specific Metrics & Purpose)
Project Progress කාර්යයන් අවසන් වීමේ ප්‍රතිශතය (%), සම්පත් භාවිත අනුපාතය, සැලසුම් කළ vs සත්‍ය වැයවූ පරිශ්‍රමය.
Test Progress Test cases සූදානම් වීමේ ප්‍රගතිය, Run කළ / Passed / Failed වූ ගණන, Execution කාලය.
Product Quality පද්ධතිය ක්‍රියාකාරීව පවතින කාලය (Availability), Response times, දෝෂ ඝනත්වය (Defect density).
Defect Metrics හමුවූ සහ නිවැරදි කළ දෝෂ ගණන, Defect Detection Percentage (DDP), දෝෂ විසඳීමේ වේගය.
Coverage Metrics Requirements coverage %, Code coverage % (Statement, Branch coverage).

5.3.2 Test Reports: Progress vs. Completion Reports FL-5.3.2 (K2)

පරාමිතිය Test Progress Report (තත්ත්ව වාර්තාව) Test Completion Report (සමාප්ති වාර්තාව)
වාර්තා කරන අවස්ථාව පරීක්ෂණ ක්‍රියාවලිය අතරතුර නිතිපතා (දිනපතා, සතිපතා හෝ sprint එකක් පාසා). ව්‍යාපෘති සන්ධිස්ථානයකදී (Milestone), Sprint එකක් අවසානයේ හෝ Release එකකදී එක්වරක් පමණි.
ප්‍රධාන අරමුණ අඛණ්ඩ Test Control සඳහා සහාය වීම; සම්පත් හා සැලසුම් වෙනස් කිරීමට තොරතුරු සැපයීම. පරීක්ෂණ ක්‍රියාවලිය සාරාංශ කිරීම, මෘදුකාංග ගුණාත්මකභාවය ඇගයීම, නිල නිමාව සනිටුහන් කිරීම.
අඩංගු වන කරුණු • වත්මන් පරීක්ෂණ ප්‍රගතිය (කාලසටහනට පෙරද / පසුපසද)
• Passed/Failed test metrics සහ ඉතිරි වැඩ
• බාධාවන් (Blockers) සහ මඟහැරීමේ ක්‍රම (Workarounds)
• ඉදිරි කාලසීමාවේ සැලැස්ම 		• සමස්ත පරීක්ෂණ සාරාංශය සහ ගුණාත්මක ඇගයීම
• සැලැස්මෙන් සිදුවූ අපගමනයන් (කාලය, අයවැය)
• විසඳා නොමැති දෝෂ (Unresolved defects) සහ අවදානම්
• උගත් පාඩම් (Lessons Learned) සහ වැඩිදියුණු කිරීම්

5.3.3 Communicating the Status of Testing (පරීක්ෂණ තත්ත්වය සන්නිවේදනය කිරීම) FL-5.3.3 (K2)

පරීක්ෂණ වාර්තාකරණයේ මූලික අරමුණ වන්නේ ව්‍යාපෘති පාර්ශ්වකරුවන්ට (Stakeholders) නිවැරදි, අදාළ සහ කාලෝචිත තොරතුරු සැපයීමයි. සන්නිවේදන ක්‍රම 5ක් භාවිත වේ:

1. Verbal Communication:
• Daily stand-up meetings, කණ්ඩායම් සාකච්ඡා (Sync meetings).
2. Dashboards (දෘශ්‍ය පුවරු):
• CI/CD pipeline තත්ත්වය, Defect tracking dashboards, Kanban boards, Burndown charts.
3. Electronic Channels:
• විද්‍යුත් තැපෑල (Email), ක්ෂණික පණිවිඩ (Slack, Teams chat).
4. Online Documentation:
• Shared team wikis (Confluence), Test management tools (Jira, TestRail).
5. Formal Test Reports:
• විධිමත් Progress Reports සහ Completion Reports (ISO/IEC/IEEE 29119-3 සම්මතයට අනුව).

1.4 Configuration Management & Defect Management

5.4 Configuration Management (CM - වින්‍යාස කළමනාකරණය) FL-5.4.1 (K2)

මූලික අරමුණ: පරීක්ෂණ ලියකියවිලි, Test Cases, Scripts, Data, සහ Build පරිසරයන් Configuration Items ලෙස නම් කර, ඒවායේ අනුවාදයන් (Versions) සහ වෙනස්වීම් නිවැරදිව පාලනය කිරීම.
  • Baselines: අනුමත කරන ලද මට්ටමක් Baseline එකක් ලෙස නම් කෙරේ. පෙර ප්‍රතිඵල නැවත තහවුරු කිරීමට පෙර Baseline වෙත ආපසු යා හැක.
  • Traceability Support: අවශ්‍යතා, කේතය සහ පරීක්ෂණ අතර ද්වි-දිශා සබඳතාව (Bidirectional Traceability) ආරක්ෂා කරයි.
  • DevOps Integration: ස්වයංක්‍රීය CI/CD deployment pipelines සඳහා Configuration Management අත්‍යවශ්‍ය පදනමකි.

5.5 Defect Management (දෝෂ කළමනාකරණය) FL-5.5.1 (K3)

දෝෂයක් හඳුනාගැනීමේ සිට එය විශ්ලේෂණය, නිවැරදි කිරීම, නැවත පරීක්ෂා කිරීම (Confirmation testing) සහ අවසන් කිරීම දක්වා ක්‍රමවත් කාර්ය ප්‍රවාහයකි.

DEFECT LIFECYCLE WORKFLOW (දෝෂ ජීවන චක්‍රය)
1. Log Anomaly → 2. Analyze & Classify → 3. Assign / Fix → 4. Retest (Confirm) → 5. Close Report

Severity vs. Priority: තීරණාත්මක වෙනස (The Fundamental Distinction):

Severity (තාක්ෂණික බරපතලකම):

දෝෂය මඟින් පද්ධතියේ ක්‍රියාකාරිත්වයට සිදුවන තාක්ෂණික හානියේ තරම (e.g. Minor, Major, Critical, Blocker).

Priority (ව්‍යාපාරික හදිසිභාවය):

ව්‍යාපාරික අවශ්‍යතා මත දෝෂය කොතරම් ඉක්මනින් නිවැරදි කළ යුතුද යන හදිසිභාවය (e.g. Low, Medium, High, Immediate).

විභාග සම්භාව්‍ය උදාහරණය: සමාගමේ ප්‍රධාන වෙබ් අඩවියේ මුල් පිටුවේ සමාගම් නාමයේ අකුරු වැරදීමක් (Typo) ඇත.
• Severity: Low (පද්ධතිය crash වන්නේ නැත, තාක්ෂණික හානියක් නැත).
• Priority: Immediate / High (සමාගමේ කීර්තිනාමයට හානිවන බැවින් වහාම නිවැරදි කළ යුතුය).

Defect Report එකක අනිවාර්යයෙන් තිබිය යුතු තොරතුරු (ISO 29119-3 / FL-5.5.1):

ක්ෂේත්‍රය (Field) විස්තරය සහ අරමුණ (Description & Purpose)
Unique Identifier දෝෂ කළමනාකරණ පද්ධතියෙන් ස්වයංක්‍රීයව ලැබෙන අනන්‍ය අංකය.
Title & Summary නිරීක්ෂණය වූ ගැටලුව පිළිබඳ කෙටි, පැහැදිලි සාරාංශය.
Date, Author, Role දෝෂය සොයාගත් දිනය, වාර්තා කළ පුද්ගලයාගේ නම සහ තනතුර.
Test Object & Environment නිශ්චිත Build version එක, Module එක, OS, Browser සහ Hardware තොරතුරු.
Reproduction Steps දෝෂය නැවත ඇතිකිරීමට අනුගමනය කළ යුතු පියවර (Screenshots, Logs සමඟ).
Expected vs. Actual සිදුවිය යුතුව තිබූ නිවැරදි ප්‍රතිඵලය සහ සැබවින්ම සිදුවූ වැරදි ප්‍රතිඵලය.
Severity & Priority තාක්ෂණික බරපතලකම (Severity) සහ නිවැරදි කිරීමේ හදිසිභාවය (Priority).

  2. "Usability testing belongs in Quadrant Q4" → අසත්‍යයකි! Performance සහ Security අයත් වන්නේ Q4 (Technology-facing) වෙත වුවද, Usability testing අයත් වන්නේ Q3 (Business-facing, Critique product) වෙතයි.

  5. "Severity and Priority are identical" → අසත්‍යයකි! Severity යනු තාක්ෂණික බරපතලකමයි; Priority යනු ව්‍යාපාරික හදිසිභාවයයි.
  6. "Three-point estimation uses simple unweighted average" → අසත්‍යයකි! එය භාරිත සාමාන්‍යයකි: E = (a + 4m + b) / 6.

  8. "Test Progress Reports occur only once at the end" → අසත්‍යයකි! Progress reports පරීක්ෂාව අතරතුර නිතර නිකුත් කෙරේ; Completion reports නිකුත් කරන්නේ සන්ධිස්ථානවලදී එක්වරක් පමණි.

4. Realistic ISTQB Practice Exam Questions & Detailed Rationales (Part 1)

Question 1 [K3 - FL-5.1.4]: Using the Three-Point Estimation technique, experts provide the following test execution estimates: Most Optimistic (a) = 10 hours, Most Likely (m) = 16 hours, and Most Pessimistic (b) = 34 hours. What are the final weighted Estimate (E) and Standard Deviation (SD)?
(Three-Point Estimation ශිල්පක්‍රමය භාවිතයෙන් විශේෂඥයින් ලබාදෙන ඇස්තමේන්තු: Optimistic (a) = පැය 10, Most Likely (m) = පැය 16, Pessimistic (b) = පැය 34 වේ. අවසාන භාරිත ඇස්තමේන්තුව (E) සහ සම්මත අපගමනය (SD) කොපමණද?)
A) E = 18 hours, SD = 4 hours
B) E = 20 hours, SD = 4 hours
C) E = 18 hours, SD = 6 hours
D) E = 16 hours, SD = 2 hours
Correct Answer: A
Rationale (සිංහල + English):
PERT සූත්‍ර භාවිතයෙන් ගණනය කළ විට:
• E = (a + 4m + b) / 6 = (10 + 4(16) + 34) / 6 = (10 + 64 + 34) / 6 = 108 / 6 = පැය 18.
• SD = (b − a) / 6 = (34 − 10) / 6 = 24 / 6 = පැය 4.
එබැවින් අවසාන ඇස්තමේන්තුව වන්නේ 18 ± 4 hours (පැය 14 සිට 22 දක්වා පරාසය) වේ.

නිවැරදි පිළිතුර D. ටෙස්ටර්වරයා user story පිරිපහදු කිරීමට (acceptance criteria සහිත පරීක්ෂා කළ හැකි stories) සහභාගී වේ, product risk analysis කරයි, පරීක්ෂණ උත්සාහය (effort) ඇස්තමේන්තු කරයි, පරීක්ෂා කළ යුතු ක්‍රියාකාරී සහ non-functional අංග හඳුනාගනී සහ iteration එක තුළ පරීක්ෂණ ප්‍රවේශය සැලසුම් කරයි.
English: In release and iteration planning a tester helps to write testable user stories and acceptance criteria, performs product quality risk analysis, estimates the test effort, identifies functional and non-functional aspects to be tested and plans the testing within the iteration (Section 5.1.2).
Question 11 [K2 - FL-5.1.3]: Statement 1: "The test environment and test data are available." Statement 2: "The planned coverage level has been reached and the number of open critical defects is within the agreed limit." How are they correctly classified?
(ප්‍රකාශ 1: "පරීක්ෂණ පරිසරය සහ පරීක්ෂණ දත්ත ලබාගත හැකිය." ප්‍රකාශ 2: "සැලසුම් කළ ආවරණ මට්ටම සපුරා ඇති අතර විවෘත විවේචනාත්මක (critical) දෝෂ ගණන එකඟ වූ සීමාව තුළ පවතී." මේවා නිවැරදිව වර්ගීකරණය කර ඇත්තේ කෙසේද?)
A) Statement 1 is an entry criterion; statement 2 is an exit criterion (in agile: Definition of Ready and Definition of Done).
B) Statement 1 is an exit criterion; statement 2 is an entry criterion.
C) Both statements are entry criteria.
D) Both statements are exit criteria.
Correct Answer: A
Rationale (සිංහල + English):
නිවැරදි පිළිතුර A. Entry criteria යනු ක්‍රියාකාරකමක් ආරම්භ කිරීමට පෙර සපුරා තිබිය යුතු පූර්ව කොන්දේසි (පරීක්ෂා කළ හැකි අවශ්‍යතා, පරිසරය, දත්ත වැනි සම්පත්, test object එකේ ආරම්භක quality මට්ටම). Exit criteria යනු ක්‍රියාකාරකමක් සම්පූර්ණ බව ප්‍රකාශ කිරීමට සපුරාලිය යුතු දේ (සැලසුම් කළ පරීක්ෂණ ක්‍රියාත්මක කිරීම, ආවරණ මට්ටම, විසඳා නොමැති දෝෂ සීමාව). Agile හි මේවා Definition of Ready (entry) සහ Definition of Done (exit) ලෙස හැඳින්වේ.
English: Entry criteria are the preconditions for starting an activity (testable requirements, resources such as environments and data, initial quality of the test object). Exit criteria define what must be achieved to declare an activity complete (planned tests executed, coverage level reached, unresolved defects within an agreed limit). In agile projects they correspond to the Definition of Ready and the Definition of Done (Section 5.1.3).
Question 12 [K1 - FL-5.2.1]: How is the risk level of a risk determined?
(අවදානමක මට්ටම (risk level) තීරණය වන්නේ කෙසේද?)
A) Only by the cost of the mitigation actions.
B) Only by the number of testers available.
C) By combining the likelihood of the risk occurring and its impact (for example with a risk matrix or numeric ratings).
D) Only by the duration of the project.
Correct Answer: C
Rationale (සිංහල + English):
නිවැරදි පිළිතුර C. Risk level එක තීරණය වන්නේ අවදානම සිදුවීමේ ඉඩකඩ (likelihood — සම්භාවිතාව, 0 ට වැඩි 1 ට අඩු) සහ එහි බලපෑම (impact — සිදුවීමේ ප්‍රතිවිපාක) ඒකාබද්ධ කිරීමෙනි; මෙය ගුණාත්මකව (high/medium/low) හෝ සංඛ්‍යාත්මකව ප්‍රකාශ කළ හැකිය.
English: The risk level is determined by risk likelihood (the probability that the risk occurs, greater than zero and less than one) and risk impact (the consequences of its occurrence). It can be expressed qualitatively (high/medium/low) or quantitatively (Section 5.2.1).
Question 13 [K2 - FL-5.2.3]: A product risk analysis rates the payment module as high risk and the "About us" page as low risk. How should these results influence testing?
(Product risk analysis මගින් ගෙවීම් මොඩියුලය ඉහළ අවදානම් ලෙසත් "About us" පිටුව අඩු අවදානම් ලෙසත් ඇගයී ඇත. මෙම ප්‍රතිඵල පරීක්ෂාවට බලපාන්නේ කෙසේද?)
A) Both should receive identical effort to stay fair.
B) The payment module gets more thorough techniques, higher coverage and earlier testing; the "About us" page gets minimal effort.
C) The payment module should be skipped because high-risk items are too expensive to test.
D) The "About us" page should be tested first because it is the easiest.
Correct Answer: B
Rationale (සිංහල + English):
නිවැරදි පිළිතුර B. Risk analysis ප්‍රතිඵල මගින් පරීක්ෂණ විෂය පථය, මට්ටම් සහ වර්ග, භාවිත කළ යුතු තාක්ෂණ සහ ආවරණ මට්ටම, කාර්යයකට අවශ්‍ය උත්සාහය සහ ප්‍රමුඛතා (විවේචනාත්මක දෝෂ හැකිතාක් කලින් සොයාගැනීමට) තීරණය කෙරේ. ඉහළ අවදානම් ගෙවීම් මොඩියුලයට වඩා ගැඹුරු පරීක්ෂාවක් සහ කලින් පරීක්ෂාවක් ද, අඩු අවදානම් පිටුවට අවම උත්සාහයක් ද ලැබේ.
English: Product risk analysis results are used to decide the test scope, the test levels and types, the test techniques and coverage, the test effort per task, and the priorities so that critical defects are found as early as possible; they may also point to non-testing activities that reduce risk. Higher risk means more thorough and earlier testing (Section 5.2.3).
Question 14 [K2 - FL-5.2.4]: A product risk analysis identifies a high security risk. Which of the following is an appropriate response measure?
(Product risk analysis මගින් ඉහළ security අවදානමක් හඳුනාගෙන ඇත. සුදුසු ප්‍රතිචාරාත්මක ක්‍රියාමාර්ගයක් කුමක්ද?)
A) Reduce the test effort to meet the schedule, because security defects are rare.
B) Remove the security requirement from the test basis.
C) Assign testers with suitable security skills, apply security testing and static analysis, and increase the independence of testing.
D) Wait for a production incident and fix the problem afterwards.
Correct Answer: C
Rationale (සිංහල + English):
නිවැරදි පිළිතුර C. අවදානම්වලට ප්‍රතිචාර ලෙස: අදාළ අවදානම් වර්ගයට සුදුසු අත්දැකීම් සහ කුසලතා ඇති ටෙස්ටර්වරුන් තෝරා ගැනීම, සුදුසු ස්වාධීනත්ව මට්ටමක් යෙදීම, reviews සහ static analysis කිරීම, සුදුසු තාක්ෂණ සහ ආවරණ මට්ටම් භාවිතය, බලපෑමට ලක්වන quality ලක්ෂණ ආවරණය කරන පරීක්ෂණ වර්ග (security testing වැනි) යෙදීම, සහ regression testing ඇතුළු dynamic testing සිදු කිරීම.
English: Measures in response to analyzed product risks include: choosing testers with the right experience and skills for the risk type, applying an appropriate level of independence, performing reviews and static analysis, applying suitable test techniques and coverage levels, applying test types addressing the affected quality characteristics (such as security testing), and performing dynamic testing including regression testing (Section 5.2.4).
Question 15 [K1 - FL-5.3.1]: Which of the following is a TEST PROGRESS metric?
(පහත සඳහන් ඒවායින් පරීක්ෂණ ප්‍රගති මෙට්‍රික (test progress metric) එකක් කුමක්ද?)
A) Mean time to failure of the released product.
B) The number of test cases run and not run, passed and failed.
C) Defect density.
D) Cost of quality.
Correct Answer: B
Rationale (සිංහල + English):
නිවැරදි පිළිතුර B. Test progress metrics: ක්‍රියාත්මක කළ/නොකළ test cases ගණන, pass/fail ගණන, test case implementation ප්‍රගතිය, test environment සූදානම සහ test execution කාලය. Mean time to failure යනු product quality metric එකකි; defect density යනු defect metric එකකි; cost of quality යනු cost metric එකකි.
English: Test progress metrics include the number of test cases run / not run, passed / failed, test case implementation progress, test environment preparation progress and test execution time. Mean time to failure is a product quality metric, defect density is a defect metric and cost of quality is a cost metric (Section 5.3.1).
Question 16 [K2 - FL-5.3.3]: A distributed agile team (three countries) uses a CI/CD pipeline. Which is the most suitable way to communicate the status of testing continuously?
(රටවල් තුනක විසිරී සිටින agile කණ්ඩායමක් CI/CD pipeline එකක් භාවිත කරයි. පරීක්ෂණ තත්ත්වය අඛණ්ඩව සන්නිවේදනය කිරීමට වඩාත් සුදුසු ක්‍රමය කුමක්ද?)
A) Printing a monthly test report and sending it by post.
B) Hallway conversations only.
C) Waiting until the end of the project to present the test completion report.
D) Dashboards (for example CI/CD dashboards, task boards and burn-down charts), supported by chat, online documentation and short verbal updates.
Correct Answer: D
Rationale (සිංහල + English):
නිවැරදි පිළිතුර D. පරීක්ෂණ තත්ත්වය සන්නිවේදනය කළ හැකි ක්‍රම: වාචික සන්නිවේදනය, dashboards (CI/CD dashboards, task boards, burn-down charts), ඉලෙක්ට්‍රොනික නාලිකා (email, chat), online ලේඛන සහ විධිමත් test reports. ක්‍රමය තෝරාගැනීම ප්‍රේක්ෂකයින්, ව්‍යාපෘති අවදානම, සංවිධාන ප්‍රමිතීන් සහ කණ්ඩායම විසිරී පවතීද යන්න මත රඳා පවතී. විසිරුණු agile කණ්ඩායමකට dashboards සහ chat වැනි අඛණ්ඩ ක්‍රම වඩාත් සුදුසුය.
English: Ways to communicate test status include verbal communication, dashboards (CI/CD dashboards, task boards, burn-down charts), electronic channels (e-mail, chat), online documentation and formal test reports. The choice depends on the audience, project risk, organizational standards and whether the team is distributed. A distributed agile team benefits from continuous, shared channels such as dashboards and chat (Section 5.3.3).
