Chapter 01: Fundamentals of Testing (පරීක්ෂාවේ මූලධර්ම)

1. Core Syllabus Concepts & In-Depth Notes (ප්‍රධාන විෂය කරුණු විස්තරාත්මකව)

1.1 What is Testing? (මෘදුකාංග පරීක්ෂාව යනු කුමක්ද?) FL-1.1.1 FL-1.1.2

Formal Definition (විධිමත් අර්ථ දැක්වීම): Software testing යනු මෘදුකාංගයක ඇති defects (දෝෂ) හඳුනා ගැනීමට සහ එහි quality (ගුණාත්මකභාවය) ඇගයීමට සිදු කරනු ලබන සැලසුම් සහගත ක්‍රියාකාරකම් සමූහයකි (set of activities to discover defects and evaluate quality). මෙලෙස පරීක්ෂාවට ලක්වන ඕනෑම work product එකක් නිල වශයෙන් test object එකක් ලෙස හඳුන්වයි.

මෘදුකාංග පද්ධති අද වන විට මිනිස් ජීවිතයේ සෑම අංශයකටම සම්බන්ධ වී ඇත. වැරදි සහිත මෘදුකාංග නිසා මුදල් නාස්තිය, කාලය නාස්ති වීම, ආයතනික කීර්ති නාමය පිරිහීම පමණක් නොව ජීවිත හානි පවා සිදුවිය හැක (උදා: වෛද්‍ය උපකරණ, ගුවන් යානා පාලන පද්ධති). පරීක්ෂාව මගින් පද්ධතියේ අවදානම (risk) අවම කර විශ්වාසය තහවුරු කරයි.

Common Misconception #1 (වැරදි වැටහීම 1):
"Testing කියන්නේ Software එක run කරලා outputs බලන එක විතරයි."
යථාර්ථය (Reality): Testing යනු test execution පමණක් නොවේ. Planning (සැලසුම් කිරීම), Analysis, Design, Implementation, Monitoring, Control සහ Completion යන සමස්ත ක්‍රියාවලියම මීට අයත් වේ. තවද code එක run නොකර සිදුකරන Static Testing (reviews) ද මීට ඇතුළත් වේ.
Common Misconception #2 (වැරදි වැටහීම 2):
"Testing මගින් සිදුකරන්නේ Verification පමණයි."
යථාර්ථය (Reality): Testing වලදී Verification (ලියකියවිලි වලට අනුව හැදුවාද බැලීම) සහ Validation (පරිශීලකයාගේ සැබෑ අවශ්‍යතා සපුරාලනවාද බැලීම) යන දෙකම එක හා සමානව සිදුකරයි.

Verification vs. Validation: මූලික වෙනස

මානය (Dimension) Verification ("Building it Right?") Validation ("Building the Right Thing?")
ප්‍රධාන අරමුණ පද්ධතිය දී ඇති specifications සහ requirements වලට අනුකූලව නිර්මාණය කර ඇත්දැයි බැලීම. පද්ධතිය පරිශීලකයාගේ සැබෑ operational needs සහ business goals සපුරාලන්නේදැයි බැලීම.
මූලාශ්‍රය (Basis) Requirements documents, Design specifications, Architecture diagrams. Real user workflows, Operational environment, User expectations.
විභාග උදාහරණය Spec එකේ සඳහන් formula එකට අනුව discount එක හැදෙනවාදැයි පරීක්ෂා කිරීම. සැබෑ පාරිභෝගිකයෙකුට checkout flow එක පහසුවෙන් සහ අපහසුවකින් තොරව භාවිත කළ හැකිදැයි බැලීම.

Testing ප්‍රධාන කොටස් දෙකකට බෙදිය හැක: Dynamic Testing (කේතය run කර සිදුකරන පරීක්ෂා) සහ Static Testing (කේතය run නොකර ලියකියවිලි හා කේත කියවා විමර්ශනය කිරීම). Testing යනු හුදු යාන්ත්‍රික වැඩක් නොව ගැඹුරු විශ්ලේෂණාත්මක බුද්ධිමය කාර්යයකි (intellectual activity).

The 9 Typical Test Objectives (පරීක්ෂාවේ ප්‍රධාන අරමුණු 9) FL-1.1.1 (K1)

ISTQB CTFL v4.0.1 syllabus එකට අනුව පරීක්ෂාව සිදුකිරීමේ නිල අරමුණු 9ක් හඳුනාගෙන ඇත:

1. Evaluating Work Products

Requirements, user stories, designs, architecture සහ code සංවර්ධනයට පෙර හා අතරතුරදී ඇගයීම.

2. Triggering Failures & Finding Defects

Dynamic tests මගින් failures ඇති කිරීම සහ static testing මගින් defects සෘජුවම සොයා ගැනීම.

3. Ensuring Required Coverage

අවශ්‍ය requirements හෝ code structure නිශ්චිත coverage සීමාවන්ට අනුව පරීක්ෂා වී ඇති බව තහවුරු කිරීම.

4. Reducing Risk Level

මෘදුකාංගය operational පරිසරයේදී අසාර්ථක වීමේ අවදානම (software risk) කල්තියා අවම කිරීම.

5. Verifying Requirements

පද්ධතිය ගිවිසගත් සියලු functional සහ non-functional requirements සපුරා ඇති බව තහවුරු කිරීම.

6. Validating Test Object

මෘදුකාංගය පරිශීලකයන්ගේ සහ පාර්ශ්වකරුවන්ගේ (stakeholders) සැබෑ අපේක්ෂා ඉටුකරන බව තහවුරු කිරීම.

7. Providing Decision Information

මෘදුකාංගය release කිරීමට සූදානම්ද යන්න පිළිබඳව තීරණ ගැනීමට stakeholders වෙත නිවැරදි තොරතුරු සැපයීම.

8. Building Confidence

පරීක්ෂණ සාර්ථකව සමත් වීම මගින් මෘදුකාංගයේ ගුණාත්මකභාවය පිළිබඳව විශ්වාසය ගොඩනැගීම.

9. Complying with Standards

නෛතික, නියාමන (regulatory), හෝ ආරක්ෂක ප්‍රමිතීන්ට (ISO standards) පද්ධතිය අනුකූල බව පෙන්වීම.

1.1.2 Testing vs. Debugging (පරීක්ෂාව සහ Debugging අතර වෙනස) FL-1.1.2

Software Testing (පරීක්ෂාව):

පද්ධතියේ defects නිසා සිදුවන failures ප්‍රදර්ශනය කිරීම සහ quality එක ඇගයීම අරමුණු කරයි. Testing සිදුකරන්නේ ප්‍රධාන වශයෙන් Testers ලා විසිනි. Testing මගින් කේතය වෙනස් කරන්නේ නැත.

Debugging (දෝෂ විශ්ලේෂණය හා නිවැරදි කිරීම):

Failure එකක් වාර්තා වූ පසු Developers ලා විසින් සිදුකරන ක්‍රියාවලියකි:
• 1. Reproduction: Failure එක නැවත සිදුවන බව තහවුරු කිරීම.
• 2. Diagnosis: Defect එක කේතයේ කොතැනදැයි සොයා ගැනීම (Root cause).
• 3. Fixing: කේතය වෙනස් කර දෝෂය ඉවත් කිරීම.

විභාග සටහන: Debugging අවසන් වූ පසු, දෝෂය නිවැරදිව විසඳී ඇත්දැයි බැලීමට tester විසින් Confirmation Testing (re-testing) සිදුකරන අතර, අතුරු ආබාධ ඇති වී ඇත්දැයි බැලීමට Regression Testing සිදුකරයි.

1.2 Why is Testing Necessary? (පරීක්ෂාව අත්‍යවශ්‍ය වන්නේ ඇයි?) FL-1.2.1 FL-1.2.2

Testing සහ Quality Assurance (QA) අතර වෙනස:
• Quality Assurance (QA): ක්‍රියාවලි කේන්ද්‍රීයයි (Process-oriented). මුළු සංවර්ධන ක්‍රියාවලියම නිවැරදිව පවත්වා ගනිමින් දෝෂ ඇතිවීම වැළැක්වීම (prevention) අරමුණු කරයි.
• Quality Control (QC): නිෂ්පාදන කේන්ද්‍රීයයි (Product-oriented). නිමි භාණ්ඩයේ හෝ artifact එකේ දෝෂ සොයා ගැනීම (detection) අරමුණු කරයි. Testing යනු QC හි ප්‍රධාන කොටසකි.

1.2.3 Errors, Defects, Failures, and Root Causes (හේතු-ඵල දාමය) FL-1.2.3 (K2)

ISTQB හි මූලිකම සංකල්පීය දාමය පහත පරිදි ක්‍රියාත්මක වේ:

සංකල්පය (Term) නිල අර්ථ දැක්වීම (Syllabus Definition) ප්‍රායෝගික උදාහරණය (Real-world Scenario)
Root Cause (මූලික හේතුව) මිනිස් අතපසුවීමකට මග පාදන මූලික සාධකය හෝ පරිසරය (Fundamental reason). Developer අධික වෙහෙසට පත්ව සිටීම (fatigue), සංකීර්ණ තාක්ෂණය නොදැනීම, කාලය මදිවීම.
Error / Mistake (මිනිස් අතපසුවීම) මිනිසෙකු විසින් සිදුකරන වැරදි ක්‍රියාවක් (Human action that produces an incorrect result). Developer විසින් කේතයේ <= වෙනුවට < ලෙස වැරදියට ටයිප් කිරීම.
Defect / Bug / Fault (දෝෂය) Error එකක් නිසා work product එකක (code/doc) ඇතිවන අඩුපාඩුව. Source code එකෙහි ඇති වැරදි logical statement එක.
Failure (පද්ධති අසාර්ථක වීම) Defect එකක් ක්‍රියාත්මක වීම නිසා පද්ධතියේ ක්‍රියාකාරීත්වය අපේක්ෂිත මට්ටමෙන් බැහැරවීම (Observable event). Customer checkout කරන විට system එක crash වීම හෝ වැරදි ගණනයක් පෙන්වීම.
විභාග රීතිය: සෑම Defect එකක්ම Failure එකකට මග පාදන්නේ නැත (උදා: කවදාවත් execute නොවෙන dead code එකක ඇති defect එකක් failure එකක් ඇති නොකරයි). එසේම පාරිසරික බලපෑම් (radiation, hardware glitch) නිසාද මිනිස් defect එකකින් තොරව failures ඇතිවිය හැක.

2. The Seven Testing Principles (පරීක්ෂණ මූලධර්ම 7) FL-1.3.1

වසර ගණනාවක මෘදුකාංග ඉංජිනේරු අත්දැකීම් මත පදනම් වූ මෙම මූලධර්ම 7 විභාගයේදී නිතර අසනු ලැබේ:

Principle 1: Testing shows presence, not absence of defects

පරීක්ෂාව මගින් මෘදුකාංගයේ දෝෂ ඇති බව පෙන්විය හැක. නමුත් පරීක්ෂණ 100% සමත් වුවද මෘදුකාංගයේ කිසිදු දෝෂයක් නැතැයි ඔප්පු කළ නොහැක.

Principle 2: Exhaustive testing is impossible

සියලුම inputs, combinations සහ preconditions පරීක්ෂා කිරීම (Exhaustive Testing) කළ නොහැක්කකි. එබැවින් Risk Analysis සහ Priorities මත පදනම්ව පරීක්ෂා කළ යුතුය.

Principle 3: Early testing saves time and money

මෘදුකාංග සංවර්ධනයේ මුල් අවධියේදීම (Shift Left) පරීක්ෂා කිරීමෙන් දෝෂ පසුව හමුවී නිවැරදි කිරීමට යන අධික වියදම වළක්වා ගත හැක.

Principle 4: Defects cluster together (Pareto Principle)

සාමාන්‍යයෙන් පද්ධතියක ඇති දෝෂ වලින් 80% ක්ම හමුවන්නේ මොඩියුල 20% ක් වැනි සුළු ප්‍රමාණයකිනි (Pareto 80/20 rule). සංකීර්ණ මොඩියුල වැඩිපුර පරීක්ෂා කළ යුතුය.

Principle 5: Tests wear out (පැරණි Pesticide Paradox)

එකම test cases නැවත නැවතත් run කිරීමෙන් අලුත් දෝෂ හසු නොවේ. කෘමීන් බෙහෙත් වලට හුරුවන්නාක් මෙන්, පද්ධතිය දෝෂ වලින් නිදහස් වීමට නම් test cases නිරන්තරයෙන් යාවත්කාලීන කළ යුතුය.

Principle 6: Testing is context dependent

විවිධ සන්දර්භ වලදී පරීක්ෂාව වෙනස් වේ. E-commerce app එකක් පරීක්ෂා කරන ආකාරය සහ ගුවන් යානා පාලන පද්ධතියක් (Safety-critical) පරීක්ෂා කරන ආකාරය එකිනෙකට වෙනස්ය.

Principle 7: Absence-of-defects fallacy (දෝෂ නොමැති බවේ මුලාව):

මෘදුකාංගයක ඇති සියලුම දෝෂ නිවැරදි කළද, එය පරිශීලකයාගේ සැබෑ අවශ්‍යතාවලට (user needs and business goals) නොගැලපේ නම් එම පද්ධතිය අසාර්ථක එකකි. Verification මෙන්ම Validation ද අත්‍යවශ්‍ය වේ.

3. Test Activities, Testware & Roles (පරීක්ෂණ ක්‍රියාවලිය, Testware සහ භූමිකාවන්) FL-1.4

The 7 Test Process Activities & Resulting Testware:

ක්‍රියාකාරකම (Activity) සිදුකරන ප්‍රධාන කාර්යය (Core Purpose) නිපදවන Testware (Deliverables)
1. Test Planning අරමුණු, විෂය පථය (scope), සම්පත් සහ කාලසටහන් නිර්ණය කිරීම. Test Plan, Test Schedule, Risk Register.
2. Test Monitoring & Test Control සැලැස්මට අනුව වැඩ සිදුවේදැයි බැලීම (Test Monitoring) සහ අපගමනයන් නිවැරදි කර ඉලක්ක කරා මෙහෙයවීම (Test Control). Test Progress Reports, Test Control Directives, Updated Risk Information.
3. Test Analysis "මොනවාද පරීක්ෂා කළ යුත්තේ?" (WHAT to test) යන්න coverage criteria අනුව තීරණය කිරීම. Prioritized Test Conditions, Defect reports on test basis.
4. Test Design "කෙසේද පරීක්ෂා කරන්නේ?" (HOW to test) යන්න අනුව test cases සෑදීම. Test Cases, Test Charters, Coverage Items, Test Data Requirements.
5. Test Implementation පරීක්ෂණ ක්‍රියාත්මක කිරීමට අවශ්‍ය පරිසරය, automated scripts සහ procedures සැකසීම. Test Procedures, Manual and Automated Test Scripts, Test Suites, Test Data, Test Execution Schedule.
6. Test Execution Test suites ක්‍රියාත්මක කිරීම, actual results හා expected results සැසඳීම. Test Logs, Defect Reports (දෝෂ වාර්තා).
7. Test Completion අවසන් දත්ත එක්රැස් කිරීම, පාඩම් උගත් දෑ (lessons learned) වාර්තා කිරීම, testware archive කිරීම. Test Completion Report, Documented Lessons Learned, Action items for improvement.

1.4.2 Test Process in Context (පරීක්ෂණ ක්‍රියාවලියට බලපාන සන්දර්භගත සාධක) FL-1.4.2 (K2)

පරීක්ෂණ ක්‍රියාවලිය තනිව හුදකලාව සිදු නොවේ. එය පහත ප්‍රධාන සාධක 8 මත පදනම්ව වෙනස් වේ:

  • Stakeholders: ව්‍යාපාරික අවශ්‍යතා, අපේක්ෂාවන් සහ ඔවුන්ගේ ලබාගත හැකි බව.
  • Team Members: කණ්ඩායමේ කුසලතා, පළපුරුද්ද සහ පුහුණු අවශ්‍යතා.
  • Business Domain: මෘදුකාංගයේ වැදගත්කම, අවදානම් සහ නීතිමය රෙගුලාසි.
  • Technical Factors: මෘදුකාංග වර්ගය, Architecture සහ භාවිත වන තාක්ෂණය.
  • Project Constraints: කාලය, අයවැය (budget), සහ සම්පත් සීමාවන්.
  • Organizational Factors: ආයතනික ව්‍යුහය, ප්‍රතිපත්ති (policies) සහ භාවිතයන්.
  • SDLC Model: Sequential (Waterfall), Agile, හෝ DevOps pipelines.
  • Tooling: පවතින Test tools, ඒවායේ හැකියාව සහ ගැළපීම.

1.4.4 Traceability between the Test Basis and Testware FL-1.4.4 (K2)

ද්විපාර්ශ්වික සොයාගැනීමේ හැකියාව (Bidirectional Traceability):

Requirements ↔ Test Conditions ↔ Test Cases ↔ Test Results ↔ Logged Defects අතර සෘජු සබඳතාවක් පවත්වා ගැනීම.
• Coverage Evaluation: අවශ්‍යතා කොපමණ දුරට පරීක්ෂා කර ඇත්දැයි මැනිය හැක.
• Impact Analysis: අවශ්‍යතාවක් වෙනස් වූ විට නැවත run කළ යුතු test cases නිශ්චිතව හඳුනාගැනීම.
• Auditability & Reporting: විගණන අවශ්‍යතා සහ කළමනාකාරිත්වයට පැහැදිලි තත්ත්ව වාර්තා සැපයීම.

1.4.5 Roles in Testing: Test Management Role vs. Testing Role FL-1.4.5 (K2)

ලක්ෂණය (Attribute) Test Management Role (කළමනාකරණ භූමිකාව) Testing Role (තාක්ෂණික ඉංජිනේරු භූමිකාව)
ප්‍රධාන වගකීම සමස්ත පරීක්ෂණ ක්‍රියාවලිය, කණ්ඩායම මෙහෙයවීම සහ නායකත්වය ලබාදීම. පරීක්ෂාවේ තාක්ෂණික සහ ඉංජිනේරුමය (Engineering) අංශය ක්‍රියාත්මක කිරීම.
අදාළ ක්‍රියාකාරකම් Test Planning, Test Monitoring, Test Control, සහ Test Completion. Test Analysis, Test Design, Test Implementation, සහ Test Execution.
Agile පරිසරය තුළ කළමනාකරණ කාර්යයන් Agile කණ්ඩායම විසින් සාමූහිකව සිදුකරනු ලබයි. Developers සහ Product Owner සමඟ එක්ව cross-functional ලෙස කටයුතු කරයි.
භූමිකාවන් බෙදාගැනීම නම්‍යශීලී බව (Flexibility): එක් පුද්ගලයෙකුට භූමිකාවන් දෙකම එකවර දැරිය හැක, නැතහොත් විවිධ පුද්ගලයින්ට අවස්ථානුකූලව පැවරිය හැක.

1.5 Essential Skills and Good Practices in Testing

1.5.1 Generic Skills Required for Testing (ටෙස්ටර් සතු විය යුතු පොදු කුසලතා 6) FL-1.5.1 (K2)

1. Testing Knowledge: පරීක්ෂණ ක්‍රමවේද සහ ශිල්පක්‍රම පිළිබඳ දැනුම.
2. Thoroughness & Curiosity: සුපරීක්ෂාකාරී බව, කුතුහලය සහ විස්තර කෙරෙහි අවධානය.
3. Communication Skills: සක්‍රීය සවන්දීම, පැහැදිලි වාර්තාකරණය සහ සාකච්ඡා කිරීම.
4. Critical Thinking: ගැටලු විශ්ලේෂණය, edge cases සිතීම සහ තාර්කික චින්තනය.
5. Technical Knowledge: Software architectures, database, සහ test tools දැනුම.
6. Domain Knowledge: අදාළ ව්‍යාපාරික ක්ෂේත්‍රය පිළිබඳ මනා අවබෝධය.

1.5.2 The Whole Team Approach (සමස්ත කණ්ඩායමේ ප්‍රවේශය) FL-1.5.2 (K1)

Extreme Programming (XP) මඟින් බිහිවූ මූලධර්මය:

ගුණාත්මකභාවය (Quality) යනු tester ගේ පමණක් නොව developer, business analyst, product owner ඇතුළු මුළු කණ්ඩායමේම සාමූහික වගකීමකි.
• අවශ්‍ය දැනුම හා කුසලතා ඇති ඕනෑම කණ්ඩායම් සාමාජිකයෙකුට ඕනෑම පරීක්ෂණ කාර්යයක් කළ හැක.
• කණ්ඩායම එකම සේවා පරිශ්‍රයක (Co-location) සිටීමෙන් සන්නිවේදනය හා සහයෝගීතාවය උපරිම වේ.
• ටෙස්ටර්ස්ලා අනෙකුත් සාමාජිකයින්ට testing දැනුම ලබාදෙමින් මුළු කණ්ඩායමේම තත්ත්ව ප්‍රමිතිය ඉහළ නංවයි.

1.5.3 Independence of Testing: Levels, Benefits & Drawbacks FL-1.5.3 (K2)

ස්වාධීනත්වය වැඩි වන තරමට විවිධ දෝෂ හඳුනාගැනීමේ හැකියාව ඉහළ යයි, නමුත් හුදකලා වීමේ අවදානමක් පවතී:

  • Level 1 (ස්වාධීනත්වයක් නැත): Author විසින්ම තමා ලියූ code එක පරීක්ෂා කිරීම (Unit testing). තමාගේම වැරදි දැකීමේ හැකියාව අඩුය (cognitive bias).
  • Level 2 (සුළු ස්වාධීනත්වයක්): කණ්ඩායමේ සිටින සමකාලීනයෙකු (Peer Developer) විසින් පරීක්ෂා කිරීම (Peer review / pair testing).
  • Level 3 (ඉහළ ස්වාධීනත්වයක්): ආයතනය තුළ සිටින ස්වාධීන Test Team එකක් හෝ විශේෂඥ testers ලා විසින් පරීක්ෂා කිරීම.
  • Level 4 (උපරිම ස්වාධීනත්වයක්): ආයතනයෙන් පිටස්තර (External / Outsourced) හෝ certification/security විශේෂඥයන් විසින් පරීක්ෂා කිරීම.

4. Realistic ISTQB Practice Exam Questions & Detailed Rationales (අභ්‍යාස ප්‍රශ්න සහ විවරණ)

Question 1 [K1 - FL-1.1.1]: Which of the following is an official, recognized test objective according to the ISTQB syllabus?
(ISTQB විෂය නිර්දේශයට අනුව පහත සඳහන් දෑ අතුරින් නිල වශයෙන් පිළිගත් පරීක්ෂණ අරමුණක් (test objective) වන්නේ කුමක්ද?)
A) Proving that the software contains zero remaining defects.
B) Diagnosing defect causes in the source code and removing them.
C) Providing information to stakeholders to allow them to make informed decisions.
D) Demonstrating that testing was performed exhaustively across all code paths.
Correct Answer: C
Rationale (විවරණය): Stakeholders ලාට නිවැරදි තීරණ ගැනීමට අවශ්‍ය තොරතුරු සැපයීම නිල අරමුණු 9න් එකකි.
• Option A වැරදිය (Principle 1 අනුව දෝෂ නොමැති බව ඔප්පු කළ නොහැක).
• Option B යනු Debugging ක්‍රියාවලියකි (Testing නොවේ).
• Option D වැරදිය (Principle 2 අනුව සියලු code paths පරීක්ෂා කිරීම කළ නොහැක).
Question 2 [K2 - FL-1.1.2]: How does dynamic testing fundamentally differ from debugging?
(ගතික පරීක්ෂාව (Dynamic testing) සහ දෝෂ නිරාකරණය (Debugging) අතර ඇති මූලික වෙනස කුමක්ද?)
A) Dynamic testing directly detects defects in code, whereas debugging reproduces failures.
B) Dynamic testing triggers failures caused by defects, whereas debugging reproduces, diagnoses, and fixes the defects.
C) Testing is performed exclusively by developers, whereas debugging is performed by independent testers.
D) Testing eliminates defects from the software, whereas debugging measures statement coverage.
Correct Answer: B
Rationale (විවරණය): Dynamic testing මගින් software එක execute කර failures ඇතිවීම නිරීක්ෂණය කරයි. Debugging යනු එම failure එක reproduce කර, දෝෂය ඇති තැන සොයා (diagnose), එය කේතයෙන් නිවැරදි කිරීමයි (fixing).
Question 3 [K2 - FL-1.2.3]: A programmer tired from excessive overtime mistypes a logical operator in an algorithm. As a result, when an eligible customer purchases goods, the system unexpectedly crashes at checkout. What are the ERROR, DEFECT, and FAILURE in this scenario?
(අධික වෙහෙස නිසා ක්‍රමලේඛකයෙකු ඇල්ගොරිතමයක තාර්කික මෙහෙයුම්කාරකයක් (logical operator) වැරදියට ටයිප් කරයි. මෙහි ප්‍රතිඵලයක් ලෙස පාරිභෝගිකයෙකු භාණ්ඩ මිලදී ගැනීමේදී පද්ධතිය අනපේක්ෂිත ලෙස බිඳවැටේ. මෙම අවස්ථාවේ ERROR (මිනිස් අතපසුවීම), DEFECT (කේතයේ දෝෂය), සහ FAILURE (පද්ධතියේ බිඳවැටීම) නිවැරදිව හඳුනාගන්න.)
A) Error: Mistyping the operator; Defect: Flawed code in algorithm; Failure: System crash at checkout.
B) Error: Overtime fatigue; Defect: System crash; Failure: Mistyped operator.
C) Error: System crash; Defect: Mistyping the operator; Failure: Customer complaint.
D) Error: Flawed code; Defect: Mistyped operator; Failure: Customer purchases goods.
Correct Answer: A
Rationale (විවරණය):
• Error (මිනිස් අතපසුවීම): Operator එක වැරදියට ටයිප් කිරීම (Mistyping).
• Defect (කේතයේ දෝෂය): Algorithm එකේ ඇති වැරදි කේතය (Flawed code).
• Failure (පද්ධතියේ බිඳවැටීම): Checkout එකේදී system එක crash වීම. (Overtime fatigue යනු Root Cause වේ).
Question 4 [K2 - FL-1.3.1]: A project manager claims: "Since our automated regression test suite executed all 500 test cases with a 100% pass rate, our application is guaranteed to satisfy all customer expectations and need not be tested further." Which TWO testing principles refute this claim?
(ව්‍යාපාරික කළමනාකරු පවසන්නේ 500ක් වූ automated regression tests 100% සමත් වූ නිසා පාරිභෝගික අපේක්ෂා සියල්ල ඉටුවන බවත් තවදුරටත් පරීක්ෂා කිරීම අවශ්‍ය නොවන බවත්ය. මෙම ප්‍රකාශය ප්‍රතික්ෂේප කරන පරීක්ෂණ මූලධර්ම (Testing Principles) දෙක කුමක්ද?)
A) Early testing saves time and money & Defects cluster together.
B) Absence-of-defects fallacy & Testing shows presence, not absence of defects.
C) Tests wear out & Exhaustive testing is impossible.
D) Testing is context dependent & Early testing saves time and money.
Correct Answer: B
Rationale (විවරණය): 100% pass rate එකක් තිබූ පමණින් customer expectations සපුරාලන්නේ නැත (Principle 7: Absence-of-defects fallacy). තවද pass වීමෙන් දෝෂ නොමැති බව ඔප්පු නොවේ (Principle 1: Testing shows presence, not absence of defects).
Question 5 [K2 - FL-1.4.1]: In which test activity is the question "WHAT to test" answered in terms of measurable coverage criteria?

B) Test Design
C) Test Analysis
D) Test Implementation
Correct Answer: C
Rationale (විවරණය): "WHAT to test" (මොනවාද පරීක්ෂා කළ යුත්තේ) යන්න තීරණය කරන්නේ Test Analysis වලදීය (Test Conditions නිර්ණය කිරීම). "HOW to test" (කෙසේද පරීක්ෂා කරන්නේ) යන්න තීරණය කරන්නේ Test Design වලදීය (Test Cases නිර්මාණය).

Part 2: Additional Questions for Remaining Learning Objectives (ඉතිරි ඉගෙනුම් අරමුණු සඳහා අමතර ප්‍රශ්න)

Question 9 [K2 - FL-1.2.1]: Which example BEST illustrates why testing is necessary?
(පහත උදාහරණවලින් පරීක්ෂාව අවශ්‍ය වන්නේ ඇයිද යන්න වඩාත් හොඳින් පැහැදිලි කරන්නේ කුමක්ද?)
A) Testing guarantees that the released system contains no remaining defects.
B) Testing a payment module before release detects a rounding defect that would have overcharged customers, reducing the risk of financial loss and reputation damage.
C) Testing replaces the need for requirements reviews and code reviews.
D) Testing is needed only because the contract says so, not because it reduces risk.
Correct Answer: B
Rationale (සිංහල + English):
නිවැරදි පිළිතුර B. නිකුත් කිරීමට පෙර ගෙවීම් මොඩියුලය පරීක්ෂා කිරීමෙන් ගනුදෙනුකරුවන්ට වැඩියෙන් අය කිරීමට හේතුවන වටයා ගැනීමේ (rounding) දෝෂයක් හඳුනාගත හැකිය; මෙය මූල්‍ය අලාභ සහ ප්‍රතිරූපයට හානිවීමේ අවදානම අඩු කරයි. A වැරදියි (Principle 1: පරීක්ෂාවෙන් දෝෂ නොමැති බව සනාථ කළ නොහැක). C වැරදියි (reviews වැනි static testing ද අවශ්‍යයි). D වැරදියි (පරීක්ෂාවේ ප්‍රධාන අරමුණ අවදානම අඩු කිරීමයි).
English: Testing, performed at appropriate points in the SDLC, detects defects before they become failures in operation, reducing risk and contributing to software quality (Section 1.2.1). Option A violates Principle 1 (testing cannot show the absence of defects). Option C is wrong because static testing (reviews) complements dynamic testing. Option D ignores the main purpose: risk reduction.
Question 10 [K1 - FL-1.2.2]: What is the relation between testing and quality assurance (QA)?
(පරීක්ෂාව (testing) සහ තත්ත්ව සහතිකකරණය (Quality Assurance - QA) අතර සම්බන්ධය නිවැරදිව දක්වන්නේ කුමක්ද?)
A) Testing and QA are the same activity; both are product-oriented and corrective.
B) QA is a product-oriented activity that is performed only after testing has finished.
C) Testing is a form of quality control (product-oriented, corrective) that supports quality assurance, which is process-oriented and preventive.
D) QA applies only to testers, while developers are responsible for quality control only.
Correct Answer: C
Rationale (සිංහල + English):
නිවැරදි පිළිතුර C. QA යනු ක්‍රියාවලි කේන්ද්‍රීය (process-oriented) වැළැක්වීමේ (preventive) ප්‍රවේශයකි. පරීක්ෂාව යනු නිෂ්පාදිතය කේන්ද්‍ර කරගත් (product-oriented) නිවැරදි කිරීමේ (corrective) quality control (QC) ක්‍රියාකාරකමකි. පරීක්ෂණ ප්‍රතිඵල QC හි දෝෂ නිවැරදි කිරීමට ද, QA හි සංවර්ධන සහ පරීක්ෂණ ක්‍රියාවලිවල ක්‍රියාකාරීත්වය පිළිබඳ ප්‍රතිපෝෂණයක් ලෙස ද භාවිත වේ.
English: Quality management includes QA and QC. QA is a process-oriented, preventive approach focused on implementing and improving processes. QC is a product-oriented, corrective approach, and testing is a major form of QC. Test results are used in QC to fix defects and in QA as feedback on how well the development and test processes perform (Section 1.2.2).
Question 11 [K2 - FL-1.4.2]: A company that normally builds web shops starts a safety-critical medical device project that is subject to strict regulation. According to the syllabus, how will this context most likely affect the test process?
(සාමාන්‍යයෙන් වෙබ් වෙළඳසැල් සංවර්ධනය කරන ආයතනයක් දැඩි නියාමන රීතිවලට යටත් ආරක්ෂාව-තීරණාත්මක (safety-critical) වෛද්‍ය උපකරණ ව්‍යාපෘතියක් ආරම්භ කරයි. විෂය නිර්දේශයට අනුව සන්දර්භය (context) පරීක්ෂණ ක්‍රියාවලියට බලපාන්නේ කෙසේද?)
A) The test process stays identical, because test activities are generic.
B) Testing is reduced, because the regulator performs the verification.
C) The test process is adapted: for example more formal planning, stricter documentation and traceability, independent testing and stricter exit criteria.
D) Only the tools change; plans, techniques and criteria remain unchanged.
Correct Answer: C
Rationale (සිංහල + English):
නිවැරදි පිළිතුර C. සෑම ව්‍යාපෘතියකටම ගැළපෙන විශ්වීය පරීක්ෂණ ක්‍රියාවලියක් නොමැත; එය SDLC ආකෘතිය, පරීක්ෂණ මට්ටම් සහ වර්ග, product සහ project අවදානම්, ව්‍යාපාරික ක්ෂේත්‍රය, මෙහෙයුම් සීමාවන් (අයවැය, කාලය, නියාමන/ගිවිසුම් අවශ්‍යතා), සංවිධානයේ ප්‍රතිපත්ති සහ අනුගමනය කළ යුතු ප්‍රමිතීන් අනුව සකසාගනු ලැබේ. නියාමනයට යටත් safety-critical ව්‍යාපෘතියක දී වඩා විධිමත් සැලසුම්කරණය, දැඩි ලේඛනගත කිරීම සහ traceability, ස්වාධීන පරීක්ෂාව සහ දැඩි exit criteria අවශ්‍ය වේ.
English: There is no universal test process. It is tailored to the context: SDLC model, test levels and types, product and project risks, business domain, operational constraints (budget, resources, timescales, complexity, contractual and regulatory requirements), organizational policies and required standards (Section 1.4.2). A regulated safety-critical project therefore needs more rigor.

Rationale (සිංහල + English):
නිවැරදි පිළිතුර A. Test management role එක පරීක්ෂණ ක්‍රියාවලිය, පරීක්ෂණ කණ්ඩායම සහ පරීක්ෂණ ක්‍රියාකාරකම්වල නායකත්වය සඳහා සමස්ත වගකීම දරයි (සැලසුම්කරණය, අධීක්ෂණය, පාලනය, සම්පූර්ණ කිරීම). Testing role එක පරීක්ෂාවේ තාක්ෂණික (engineering) පැති වන විශ්ලේෂණය, සැලසුම්කරණය, ක්‍රියාත්මක කිරීම සහ execution සඳහා වගකීම දරයි. භූමිකා දෙකම එකම පුද්ගලයෙකු විසින් ද ඉටුකළ හැකිය.
English: The test management role takes overall responsibility for the test process, the test team and the leadership of test activities, mainly test planning, monitoring, control and completion. The testing role takes responsibility for the engineering (technical) aspects: analysis, design, implementation and execution. One person may hold both roles (Section 1.4.5).
Question 13 [K2 - FL-1.5.1]: A tester wonders what happens if a user enters a negative quantity (not mentioned in the requirements), tries it, and then explains the resulting failure to the developer in a clear, non-confrontational way. Which generic testing skills is the tester mainly demonstrating?
(ටෙස්ටර් කෙනෙක්, අවශ්‍යතාවල සඳහන් නොවූවත් භාවිතාකරුවෙකු ඍණ ප්‍රමාණයක් ඇතුළත් කළහොත් කුමක් සිදුවේදැයි කුතුහලයෙන් එය අත්හදා බලා, එහි අසාර්ථකත්වය සංවර්ධකයාට පැහැදිලිව සහ ගැටුමකින් තොරව පහදා දෙයි. මෙහිදී ඔහු ප්‍රධාන වශයෙන් පෙන්වන සාමාන්‍ය (generic) කුසලතා මොනවාද?)
A) Project budgeting and contract negotiation
B) Database administration and programming skills only
C) Legal expertise in the business domain
D) Curiosity, critical thinking and good communication skills
Correct Answer: D
Rationale (සිංහල + English):
නිවැරදි පිළිතුර D. පරීක්ෂණ සඳහා අවශ්‍ය සාමාන්‍ය කුසලතාවලට පරීක්ෂණ දැනුම, සවිස්තරාත්මක බව සහ අවධානය, කුතුහලය, විශ්ලේෂණාත්මක සහ විචාරශීලී (critical) චින්තනය, නිර්මාණශීලීත්වය, හොඳ සන්නිවේදනය (ක්‍රියාකාරීව සවන් දීම ඇතුළුව), කණ්ඩායම් සාමාජිකයෙකු ලෙස ක්‍රියා කිරීම සහ තාක්ෂණික/ක්ෂේත්‍ර දැනුම ඇතුළත් වේ. නිශ්චිතව සඳහන් නොකළ ආදානයක් අත්හදා බැලීම කුතුහලය සහ critical thinking පෙන්වන අතර, අසාර්ථකත්වය ගොඩනගන ආකාරයෙන් පැහැදිලි කිරීම සන්නිවේදන කුසලතා පෙන්වයි.
English: Generic skills required for testing include testing knowledge, thoroughness and attention to detail, curiosity, analytical and critical thinking, creativity, good communication (including active listening), being a team player, and technical and domain knowledge (Section 1.5.1). Trying an unspecified input shows curiosity and critical thinking; explaining the failure constructively shows communication skills.
Question 14 [K1 - FL-1.5.2]: Which of the following is an advantage of the whole team approach?
(සමස්ත කණ්ඩායම් ප්‍රවේශයේ (whole team approach) වාසියක් කුමක්ද?)
A) Testers work in isolation from developers so that their independence is preserved at all times.
B) Team members with different skill sets collaborate, which improves communication and synergy, and quality becomes the responsibility of the whole team.
C) Developers no longer need to review or test their own work, because testers own all quality activities.
D) The testing role disappears, so test planning is no longer needed.
Correct Answer: B
Rationale (සිංහල + English):
නිවැරදි පිළිතුර B. Whole team approach එකේදී අවශ්‍ය දැනුම සහ කුසලතා ඇති ඕනෑම කණ්ඩායම් සාමාජිකයෙකුට ඕනෑම කාර්යයක් කළ හැකිය; සෑම දෙනාම quality සඳහා වගකිව යුතුය. වාසි: සන්නිවේදනය සහ සහයෝගීතාව වැඩිවීම, විවිධ කුසලතා එකතු වීමෙන් synergy ඇතිවීම, සහ quality සමස්ත කණ්ඩායමේ වගකීමක් බවට පත්වීම.
English: In the whole team approach, any team member with the necessary knowledge and skills can perform any task, and everyone is responsible for quality. Advantages: improved communication and collaboration, synergy from leveraging different skill sets, and quality becoming everyone's responsibility (Section 1.5.2).
