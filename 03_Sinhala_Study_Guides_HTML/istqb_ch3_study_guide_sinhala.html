Chapter 03: Static Testing (ස්ථිතික පරීක්ෂාව)

1. Core Syllabus Concepts & In-Depth Notes (ප්‍රධාන විෂය කරුණු විස්තරාත්මකව)

3.1 Static Testing Basics FL-3.1.1 FL-3.1.2 FL-3.1.3

Formal Definition: Static Testing යනු මෘදුකාංග කේතය ක්‍රියාත්මක කිරීමකින් තොරව (without executing software code) ලියකියවිලි, කේත හෝ වෙනත් work products පරීක්ෂා කර දෝෂ සෙවීමේ ක්‍රියාවලියයි. මීට මිනිසුන් විසින් සිදුකරන Reviews සහ මෙවලම් (tools) මගින් සිදුකරන Static Analysis ඇතුළත් වේ.

Examinable Work Products (ස්ථිතික පරීක්ෂාවට ලක් කළ හැකි දෑ):

මිනිසෙකුට කියවිය හැකි හෝ tool එකකට parse කළ හැකි ඕනෑම work product එකක් static testing වලට ලක් කළ හැක:

  • Business requirements specifications, epics, user stories, acceptance criteria.
  • System architecture diagrams, database schemas, UI wireframes.
  • Source code (Java, Python, C++, etc.), database configuration scripts.
  • Testware: Test plans, test cases, test charters, automated test scripts.
  • User manuals, installation guides, release notes.
  • ස්ථිතික පරීක්ෂාවට ලක් කළ නොහැකි දෑ: Source code නොමැති Third-party compiled executable binaries (මිනිසෙකුට කියවිය නොහැකි, නීතිමය වශයෙන් tool එකකින් analyze කළ නොහැකි දෑ).

Differences between Static Testing and Dynamic Testing (ස්ථිතික හා ගතික පරීක්ෂාවේ වෙනස්කම්) FL-3.1.3

පරාමිතිය Static Testing (ස්ථිතික පරීක්ෂාව) Dynamic Testing (ගතික පරීක්ෂාව)
Execution (ක්‍රියාත්මක වීම) කේතය execute කරන්නේ නැත (No runtime execution). කේතය execute කරමින් පරීක්ෂා කරයි (Runtime execution).
Defect සොයාගැනීම Defects සෘජුවම (directly) හඳුනා ගනී (කේතයේ හෝ ලියවිල්ලේ ඇති තැනම). Failures ඇති කරයි; ඉන්පසු debugging මගින් defect එක සොයාගත යුතුය.
ක්‍රියාත්මක වන අවධිය ඉතා මුල් අවධියේදීම (Early in SDLC - requirements අදියරේ සිටම). Executable code සෑදූ පසුව පමණි.
හසුවන දෝෂ වර්ග Requirements නොගැලපීම්, Coding standard වැරදි, Dead code (කවදාවත් run නොවෙන code), Security vulnerabilities. Memory leaks, performance bottlenecks, dynamic calculation errors, system integration failures.
වියදම් සහ කාර්යක්ෂමතාව දෝෂ හඳුනාගැනීමට සහ fix කිරීමට යන වියදම ඉතා අඩුය (Cost-effective). Failure එකක් වූ පසු defect එක සොයා code වෙනස් කිරීමට වැඩි වියදමක් යයි.

1.2 Feedback and Review Process (සමාලෝචන ක්‍රියාවලිය) FL-3.2

5 Review Activities based on ISO/IEC 20246 (සමාලෝචන ක්‍රියාවලියේ පියවර 5):

පියවර (Activity) සිදුකරන කාර්යය (Core Responsibilities) ප්‍රතිඵලය (Deliverables)
1. Planning විෂය පථය, අරමුණු නිර්ණය කිරීම, review type තෝරා ගැනීම, සහභාගිවන්නන් සහ roles වෙන් කිරීම, Entry/Exit criteria තැබීම. Review Plan, allocated roles, schedule.
2. Review Initiation ලියකියවිලි බෙදා හැරීම, සමාලෝචකයන්ට අරමුණු පැහැදිලි කිරීම, අවශ්‍ය checklists ලබාදීම. Work product distribution, instructions.
3. Individual Review සමාලෝචකයන් (Reviewers) තනි තනිව ස්වාධීනව ලියවිල්ල කියවා potential defects සහ anomalies ලැයිස්තුගත කිරීම. Logged anomalies, reviewer notes.
4. Communication & Analysis හමුවීමක් (meeting) පවත්වා හෝ async ක්‍රමයට ලොග් කළ anomalies සාකච්ඡා කිරීම, ඒවා සැබෑ defects ද යන්න තීරණය කිරීම, ownership පැවරීම. Review meeting minutes, anomaly decision log.
5. Fixing & Reporting Author විසින් පිළිගත් defects නිවැරදි කිරීම, Review Leader විසින් fix තහවුරු කිරීම, Exit criteria සම්පූර්ණ දැයි බලා review metrics වාර්තා කිරීම. Updated work product, Review Summary Report.

The 6 Formal Review Roles (සමාලෝචන භූමිකාවන් 6) FL-3.2.3:

  • 1. Author (කර්තෘ): Work product එක ලියූ පුද්ගලයා. ප්‍රධාන කාර්යය වන්නේ හඳුනාගත් defects නිවැරදි කිරීමයි.
  • 2. Management (කළමනාකාරිත්වය): Review එක සැලසුම් කිරීමට සම්පත් සහ කාලය වෙන් කිරීම, වියදම් කාර්යක්ෂමතාව අධීක්ෂණය කිරීම.
  • 3. Facilitator / Moderator (මැදිහත්කරු): Review meeting එක මෙහෙයවයි. ආරක්ෂිත, සාමකාමී පරිසරයක් (psychological safety) පවත්වා ගනී, මතභේද සමථයකට පත් කරයි.
  • 4. Review Leader (සමාලෝචන නායකයා): සමස්ත review ක්‍රියාවලිය සංවිධානය කරයි, සහභාගිවන්නන් තෝරා ගනී, review සාර්ථකව අවසන් වූ බව තහවුරු කරයි.
  • 5. Reviewer (සමාලෝචකයා): ලියවිල්ල ගැඹුරින් අධ්‍යයනය කර anomalies හඳුනාගෙන ලොග් කරන විෂය ප්‍රවීණයන් හෝ පාර්ශ්වකරුවන්.
  • 6. Scribe / Recorder (වාර්තාකරු): රැස්වීමේදී සාකච්ඡා වන සියලුම anomalies, තීරණ, සහ minutes නිවැරදිව ලියා තබන පුද්ගලයා.
විභාගයේ අනිවාර්ය රීතිය (Golden Rule): Formal Inspection එකකදී, Author හට කිසිසේත්ම Review Leader හෝ Scribe විය නොහැක (The Author CANNOT be Review Leader or Scribe in an Inspection!). මෙය අවශ්‍ය වන්නේ පුද්ගලික පක්ෂග්‍රාහීත්වය (conflict of interest) වැළැක්වීමටය.

The 4 Review Types (සමාලෝචන වර්ග 4) FL-3.2.4:

Review Type නායකත්වය (Leadership) ප්‍රධාන අරමුණු (Key Objectives) සුවිශේෂී ලක්ෂණ (Key Distinctions)
Informal Review නියමිත නායකයෙක් නැත. Anomalies සෙවීම, ඉක්මන් අදහස් හුවමාරුව. විධිමත් ක්‍රියාවලියක් නැත (e.g. Buddy check, Pair programming). වාර්තා අවශ්‍ය නැත.
Walkthrough Author විසින් මෙහෙයවයි. Reviewers ලා දැනුවත් කිරීම (educate), සම්මුතියකට ඒම (consensus), නව අදහස් ගැනීම, defects සෙවීම. Author විසින් ලියවිල්ල පියවරෙන් පියවර විස්තර කරයි (Scenario/dry run). Individual prep විකල්ප වේ.
Technical Review පුහුණු Moderator කෙනෙකු. තාක්ෂණික ගැටලු විසඳීම, ගෘහ නිර්මාණ තීරණ (architectural decisions) ඇගයීම, defects සෙවීම. තාක්ෂණික විශේෂඥයන් (Peers / Tech Leads) සහභාගී වේ. Individual prep අනිවාර්ය වේ.
Inspection පුහුණු Moderator / Leader. උපරිම defects සංඛ්‍යාවක් සෙවීම, quality ඇගයීම, metrics එක්රැස් කිරීම. වඩාත්ම විධිමත් (Most formal). Checklists, Entry/Exit criteria, metrics භාවිත වේ. Author ට leader/scribe විය නොහැක!
Choosing the Right Review Type:

එකම work product එක විවිධ අවස්ථා වලදී review types කිහිපයකට ලක්විය හැක (උදා: මුලින් informal peer check, පසුව formal inspection). තෝරා ගැනීම ව්‍යාපෘති අවදානම, නීතිමය අවශ්‍යතා සහ budget මත රඳා පවතී.

Individual Review Techniques (ISO/IEC 20246):

Reviewers ලා තනිව කියවීමේදී භාවිත කරන ක්‍රම:
• Ad hoc: නිශ්චිත උපදෙස් රහිතව කියවීම.
• Checklist-based: දෝෂ ලැයිස්තුවක් බලා පරීක්ෂා කිරීම.
• Scenarios & Dry Runs: භාවිත අවස්ථා මවාගෙන execute කිරීම.
• Role-based: යම් භූමිකාවක (user, admin) ඇසින් බැලීම.
• Perspective-based Reading (PBR): පරිශීලකයා, නිර්මාණකරු, පරීක්ෂකයා යන විවිධ කෝණ වලින් බලා artifacts (e.g. test cases) නිර්මාණය කිරීම. පර්යේෂණ අනුව උපරිම defects හසුවන ක්‍රමයයි.

Review Success Factors & Anti-Patterns FL-3.2.5:

  • පැහැදිලි අරමුණු සහ මැනිය හැකි exit criteria තිබීම.
  • Work products කුඩා කොටස් වලට (small chunks) කඩා review කිරීම (වෙහෙසට පත් වීම වැළැක්වීමට).
  • Individual review සඳහා සහභාගිවන්නන්ට ප්‍රමාණවත් කාලයක් ලබාදීම.
  • කළමනාකාරීත්වයේ සැබෑ සහයෝගය සහ පුහුණුව ලබාදීම.
  • විභාග අනතුරු ඇඟවීම (CRITICAL ANTI-PATTERN): Review එකකදී හමුවන defect metrics භාවිතයෙන් කර්තෘවරුන්ගේ හෝ සේවකයන්ගේ කාර්යසාධනය ඇගයීම (Evaluation of participants) කිසිසේත්ම නොකළ යුතුය. එසේ කිරීමෙන් reviews කෙරෙහි බියක් ඇති වී ක්‍රියාවලිය විනාශ වේ!
STUDENT NOTES & EXAM FLASHCARD REMINDERS (සිසු සටහන් සඳහා ඉඩ)

4. Realistic ISTQB Practice Exam Questions & Detailed Rationales (අභ්‍යාස ප්‍රශ්න සහ විවරණ)

Question 1 [K1 - FL-3.1.1]: Which of the following work products is LEAST APPROPRIATE for examination using static testing?
(ස්ථිතික පරීක්ෂාව (Static Testing) මගින් පරීක්ෂා කිරීමට අවම වශයෙන් සුදුසු කාර්ය ඵලය (Work Product) කුමක්ද?)
A) A software architecture diagram detailing microservice dependencies.
B) A third-party proprietary compiled executable binary where source code is legally inaccessible.
C) A product backlog containing user stories and acceptance criteria.
D) An automated test execution script written in Python.
Correct Answer: B
Rationale (විවරණය): Source code හෝ documentation නොමැති, නීතිමය වශයෙන් reverse-engineer කළ නොහැකි compiled 3rd-party binaries මිනිසෙකුට කියවිය නොහැකි බැවින් static testing සඳහා නුසුදුසුය. Architecture, user stories, සහ test scripts සියල්ල static testing සඳහා ඉතා යෝග්‍ය වේ.
Question 2 [K2 - FL-3.1.2]: Which of the following defects is TYPICALLY detected by static testing but CANNOT be detected by dynamic testing?
(සාමාන්‍යයෙන් ස්ථිතික පරීක්ෂාවෙන් හඳුනාගත හැකි නමුත් ගතික පරීක්ෂාවෙන් (Dynamic Testing) හඳුනාගත නොහැකි දෝෂය කුමක්ද?)
A) Excessive memory leakage occurring after 48 hours of continuous server load.
B) An unreachable block of dead source code that can never be executed.
C) Slow database query response times during peak holiday transaction traffic.
D) Inaccurate calculations triggered by unexpected floating-point precision errors during runtime.
Correct Answer: B
Rationale (විවරණය): Dynamic testing ක්‍රියාත්මක වීමට නම් code එක execute විය යුතුය. කවදාවත් execute නොවන dead code (unreachable code) dynamic testing වලින් හසු නොවේ; එය හසු කරගත හැක්කේ static code analysis මගින් පමණි. Memory leaks සහ response times යනු runtime (dynamic) සංසිද්ධීන් වේ.
Question 3 [K2 - FL-3.1.3]: How does static testing fundamentally differ from dynamic testing regarding defect detection?
(දෝෂ හඳුනාගැනීම සම්බන්ධයෙන් ස්ථිතික පරීක්ෂාව සහ ගතික පරීක්ෂාව අතර ඇති මූලික වෙනස කුමක්ද?)
A) Static testing triggers failures from which defects are diagnosed, whereas dynamic testing identifies defects directly.
B) Static testing finds defects directly in work products, whereas dynamic testing causes runtime failures from which defects are determined.
C) Static testing can only be applied to executable code, whereas dynamic testing applies to documentation.
D) Static testing measures performance efficiency, whereas dynamic testing evaluates code maintainability.
Correct Answer: B
Rationale (විවරණය): Static testing මගින් ලියවිල්ලේ හෝ කේතයේ ඇති defects සෘජුවම (directly) සොයා ගනී. Dynamic testing මගින් runtime failures ඇති කරවන අතර, ඉන්පසු debugging මගින් defect එක හඳුනාගත යුතුය.
Question 4 [K1 - FL-3.2.1]: What is a primary benefit of gathering early and frequent stakeholder feedback during the SDLC?
(SDLC තුළ මුල් අවධියේදීම සහ නිරන්තරයෙන් Stakeholder ප්‍රතිපෝෂණ (Feedback) ලබාගැනීමේ ප්‍රධාන වාසිය කුමක්ද?)
A) It guarantees that the system will achieve 100% statement and branch code coverage.
B) It eliminates the need to perform component and system integration testing.
C) It prevents misunderstandings regarding requirements and ensures changes are implemented before expensive rework is required.
D) It ensures that the author of the code acts as both moderator and scribe during formal reviews.
Correct Answer: C
Rationale (විවරණය): මුල් අවධියේදී නිරන්තරයෙන් stakeholder feedback ලබාගැනීමෙන් requirements පිළිබඳ වැරදි වැටහීම් වළක්වා ගත හැකි අතර, පසුව විශාල මුදලක් වැයවන rework අවම කරගත හැක.
Question 5 [K2 - FL-3.2.2]: During which activity of the review process (ISO/IEC 20246) are anomalies discussed, their status decided, and ownership assigned?
(ISO/IEC 20246) are anomalies discussed, their status decided, and ownership assigned? (ISO/IEC 20246 සමාලෝචන ක්‍රියාවලියේදී විෂමතා (Anomalies) සාකච්ඡා කර, ඒවායේ තත්ත්වය තීරණය කර, විසඳීමේ වගකීම පවරනු ලබන්නේ කුමන ක්‍රියාකාරකමේදීද?)
A) Review initiation
B) Individual review
C) Communication and analysis
D) Planning
Correct Answer: C
Rationale (විවරණය): Log කළ anomalies සාකච්ඡා කරන්නේ, ඒවා සැබෑ defects ද යන්න තීරණය කරන්නේ සහ fix කිරීමට ownership පවරන්නේ Communication and analysis අදියරේදීය.
Question 6 [K1 - FL-3.2.3]: In an inspection, which two roles MUST NOT be performed by the author of the work product?
(විධිමත් පරීක්ෂාවකදී (Inspection) කාර්ය ඵලයේ කතුවරයා (Author) විසින් සිදු නොකළ යුතු භූමිකා (Roles) දෙක කුමක්ද?)
A) Reviewer and Manager
B) Review Leader and Scribe
C) Moderator and Reviewer
D) Scribe and Reviewer
Correct Answer: B
Rationale (විවරණය): Section 3.2.4 strictly stipulates: "In inspections, the author cannot act as the review leader or scribe." පක්ෂග්‍රාහීත්වය වැළැක්වීමට සහ දෝෂ සාධාරණව වාර්තා කිරීමට මෙය අනිවාර්ය වේ.
Question 7 [K2 - FL-3.2.4]: Which review type is led by the AUTHOR of the work product and has multiple objectives including educating reviewers, building consensus, and gathering new ideas?
(කතුවරයා විසින් මෙහෙයවනු ලබන, සමාලෝචකයින් දැනුවත් කිරීම, එකඟතාව ගොඩනැගීම සහ නව අදහස් ලබාගැනීම අරමුණු කරගත් සමාලෝචන වර්ගය (Review Type) කුමක්ද?)
A) Walkthrough
B) Inspection
C) Technical Review
D) Informal Review
Correct Answer: A
Rationale (විවරණය): Author විසින් මෙහෙයවනු ලබන (Author-led), සමාලෝචකයන් දැනුවත් කිරීම, එකඟතාවකට පැමිණීම සහ නව අදහස් එක්රැස් කිරීම අරමුණු කරගත් review type එක වන්නේ Walkthrough ය.
Question 8 [K1 - FL-3.2.5]: Which of the following is an ANTI-PATTERN that directly undermines the success of a review program?
(සමාලෝචන වැඩසටහනක සාර්ථකත්වයට සෘජුවම බාධා පමුණුවන ප්‍රති-රටාවක් (Anti-pattern) වන්නේ කුමක්ද?)
A) Conducting reviews on small chunks to avoid reviewer fatigue.
B) Using defect metrics gathered from reviews to evaluate the performance of participating authors.
C) Providing adequate preparation time for participants to perform individual reviews.
D) Having a trained moderator facilitate review meetings to maintain a safe environment.
Correct Answer: B
Rationale (විවරණය): Reviews වලින් හමුවන defect metrics භාවිතයෙන් authors ලාගේ performance ඇගයීම (Evaluation of participants) review culture එක මුළුමනින්ම විනාශ කරන බරපතල anti-pattern එකකි.
