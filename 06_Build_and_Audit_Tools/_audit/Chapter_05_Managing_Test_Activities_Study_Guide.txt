Looks ahead to product release; refines the

Looks ahead to a single iteration (sprint

• Detailed risk analysis of individual user stories.

• Assessing testability of user stories.

• Breaking down user stories into testing tasks.

• Estimating test effort for all testing tasks.

• Identifying functional and non-functional
aspects.

5.1.4 Test Effort Estimation Techniques FL-5.1.4 (K3)

Test effort estimation predicts the amount of work required to achieve test objectives. Estimating smaller
decomposed tasks is significantly more accurate than estimating large tasks. The syllabus defines four core
techniques:

1. Estimation Based on Ratios (Metrics-Based):

Collects figures from previous organizational
projects to establish standard ratios.

Worked Example: If historical development-to-
test effort ratio is 3 : 2, and current project dev
effort is expected to be 600 person-days:

Test Effort = 600 × (2 / 3) = 400 person-days

2. Extrapolation (Metrics-Based):

Measurements gathered early in the current
project are extrapolated forward using a
mathematical model. Highly suitable for
iterative/Agile SDLCs.

Worked Example: If actual test effort in sprints
1, 2, and 3 was 18, 22, and 20 days, sprint 4 is
estimated as the average:

Sprint 4 Effort = (18 + 22 + 20) / 3 = 20
person-days

3. Wideband Delphi (Expert-Based):

An iterative consensus technique where experts
make estimates in isolation. Results are collated.
If deviations exceed agreed boundaries, experts
discuss and submit revised estimates
anonymously until consensus is reached.

• Planning Poker: An Agile variant of Wideband
Delphi using cards representing story points or
effort size.

4. Three-Point Estimation (PERT / Expert-
Based):

Experts provide three estimates:

• a = Most optimistic estimate

• m = Most likely estimate

• b = Most pessimistic estimate

Weighted Mean Estimate (E) and Standard
Deviation (SD):

E = (a + 4m + b) / 6 | SD = (b − a) / 6

=====PAGE 2=====
Worked Permutation Example: Three-Point Estimation Calculation

Scenario: Three experts estimate testing a payment integration. Optimistic a = 6 hours, Most likely m =
9 hours, Pessimistic b = 18 hours.

Step 1 (Calculate Weighted Estimate E):

• E = (6 + 4(9) + 18) / 6 = (6 + 36 + 18) / 6 = 60 / 6 = 10 person-hours

Step 2 (Calculate Measurement Error / Standard Deviation SD):

• SD = (18 − 6) / 6 = 12 / 6 = 2 person-hours

Final Reported Estimate: 10 ± 2 person-hours (High confidence interval: between 8 and 12 hours).

CRITICAL EXAM OVERRIDE: Test Case Dependencies & Resource Constraints:

Even if a test case has the highest risk or requirement priority, if it has technical dependencies on a
lower-priority test case, the lower-priority test case MUST be executed first! Furthermore, execution
order must account for resource availability (specialized hardware, test environments, or SMEs available
only in specific time windows).

5.1.6 The Test Pyramid FL-5.1.6 (K1)

Core Concept (Cohn 2009): The test pyramid models test granularity, test isolation, and effort allocation.
It illustrates that different test objectives are supported by different levels of automation.

=====PAGE 3=====
THE TEST PYRAMID LAYERS

▲ Top: UI / End-to-End Tests (Few,
Complex, Slow, Low Isolation)

▲ Middle: Service / Integration Tests (Moderate speed &
isolation)

▲ Bottom: Unit / Component Tests (Many, Small, Fast, High Isolation)

Key Pyramid Mechanics (Syllabus Errata Precision):

Bottom Layer (Unit): Tests are small, highly isolated, fast, and test narrow functionality. Many tests are
required to achieve reasonable coverage.

Top Layer (UI / E2E): Tests are complex, high-level, slow, and check large end-to-end functionality. Only a
few are needed for coverage.

🚨 Exam Rule: The higher the layer, the lower the test granularity, the lower the test isolation, and the
higher the execution time!

5.1.7 The Testing Quadrants FL-5.1.7 (K2)

Origin & Purpose (Brian Marick 2003, Crispin 2008): The testing quadrants model groups test levels
with appropriate test types, activities, and techniques in Agile software development. It enables test
management to ensure that all test types are represented and communicate testing scope across business
and technical team members.

The model combines two orthogonal dimensions: (1) Business Facing vs. Technology Facing, and (2)

Supporting the Team (guide development) vs. Critiquing the Product (evaluating against
expectations):

Quadrant Q1: Technology Facing • Support Team

• Test Types: Component testing (unit) and component integration testing.

• Characteristics: Highly automated; embedded directly into the Continuous Integration (CI) build pipeline.

• Goal: Guides developer coding and verifies fundamental code correctness.

Quadrant Q2: Business Facing • Support Team

• Test Types: Functional tests, examples, user story tests, user experience prototypes, API testing, simulations.

• Characteristics: Validates user story acceptance criteria; can be manual or automated.

• Goal: Guides business-aligned feature development.

Quadrant Q3: Business Facing • Critique Product

• Test Types: Exploratory testing, usability testing, User Acceptance Testing (UAT).

• Characteristics: User-oriented, human evaluation; predominantly manual.

• Goal: Evaluates actual user experience and business fitness in realistic scenarios.

Quadrant Q4: Technology Facing • Critique Product

• Test Types: Smoke tests and non-functional tests (performance efficiency, reliability, security,
maintainability).

• Exception: Usability is in Q3; all other non-functional testing resides in Q4!

• Characteristics: Tool-driven; heavily automated.

1.2 Risk Management

Formal Definition (ISO 31000): A risk is a potential event, hazard, threat, or situation whose occurrence
causes an adverse effect. The test approach where activities are selected, prioritized, and managed based
on risk analysis and control is called risk-based testing.

5.2.1 Risk Definition and Attributes FL-5.2.1 (K1)

A risk is defined by two fundamental factors:

Risk Likelihood: The probability of occurrence (0 < Likelihood < 1).

Risk Impact (Harm): The potential damage or consequence if the event occurs.

Risk Level: The quantitative or qualitative measure of risk: Risk Level = Likelihood × Impact

5.2.3 Product Risk Analysis FL-5.2.3 (K2)

Core Purpose: Provides an awareness of product risks to focus testing in a way that minimizes residual
risk. It consists of two sub-activities: Risk Identification and Risk Assessment.

1. Risk Identification:

Generating a comprehensive list of potential
risks using brainstorming workshops,
stakeholder interviews, expert checklists, and
cause-effect diagrams.

2. Risk Assessment:

Categorizing risks, determining likelihood and
impact, calculating risk level, and prioritizing
risks.

• Quantitative: Multiplying numerical likelihood
by impact.

• Qualitative: Plotting on a Risk Matrix (Low,
Med, High).

How Product Risk Analysis Influences Testing Scope & Thoroughness:

Determines Test Scope: Higher-risk features receive extensive testing; low-risk areas receive minimal or
no testing.

=====PAGE 6=====
Determines Test Levels & Types: Critical security risks dictate dedicated penetration and vulnerability
testing.

Determines Test Techniques: High-risk logic warrants rigorous 3-value BVA and branch coverage; lower
risks use exploratory testing.

Estimates Effort: Guides effort allocation toward components with the highest risk ratings.

Prioritizes Test Execution: High-risk tests run first to find critical defects as early as possible.

Identifies Non-Testing Actions: Prompts training, prototyping, or code refactoring to reduce risk
upstream.

5.2.4 Product Risk Control FL-5.2.4 (K2)

Core Purpose: Encompasses all measures taken in response to identified and assessed risks. Comprises

Risk Mitigation (implementing actions to lower risk) and Risk Monitoring (tracking effectiveness and
discovering emerging risks).

Once risks are assessed, organizations choose from four response options (Veenendaal 2012):

1. Risk Mitigation

Taking active steps
(e.g. testing) to
reduce likelihood or
impact.

2. Risk Acceptance

Consciously deciding
to live with the risk
without action.

3. Risk Transfer

Passing risk to third
parties (insurance,
vendor warranty).

4. Contingency Plan

Pre-planned
response if the risk
occurs (disaster
recovery).

Actions Taken to Mitigate Product Risk via Testing:

Assigning testers with the right experience, domain
skills, and technical expertise.

Applying an appropriate degree of test
independence.

Performing static testing (requirements reviews,
code static analysis).

Selecting rigorous test techniques and setting high
coverage thresholds.

Applying dedicated non-functional test types (load,
stress, penetration).

Conducting extensive automated regression
testing.

1.3 Test Monitoring, Test Control and Test Completion

Test Monitoring:

Ongoing activity of gathering information about
testing, assessing progress against the test plan,
and tracking exit criteria achievement.

Test Control (Control Directives):

Taking corrective actions based on monitoring
data to guide testing toward its objectives (e.g.
reprioritizing tests when risks become issues,
reallocating staff).

1.4 Configuration Management & Defect Management

5.4 Configuration Management (CM) FL-5.4.1 (K2)

Purpose: Provides a discipline for identifying, controlling, tracking, and versioning all testware items (test
plans, test cases, scripts, results, environments) as configuration items.

Baselines: An approved configuration item becomes a baseline that can only be altered through formal
change control. Enables reverting to previous configurations to reproduce earlier test results.

Traceability Support: CM ensures all test items (parts of test object) and software documentation items
are uniquely identified and referenced unambiguously throughout testware.

DevOps Integration: Automated configuration management is an integral foundation of automated
CI/CD deployment pipelines.

5.5 Defect Management FL-5.5.1 (K3)

An established defect management process provides a standardized workflow from defect discovery through
analysis, classification, remediation, and closure.

DEFECT LIFECYCLE WORKFLOW

1. Log Anomaly → 2. Analyze & Classify → 3. Assign / Fix → 4. Confirmation Test → 5. Close Report

Severity vs. Priority: The Fundamental Distinction:

Severity (Technical Impact):

The degree of impact the defect has on system
operation or user requirements (e.g. Minor,
Major, Critical, Blocker).

Priority (Business Urgency):

The urgency with which the defect must be fixed
based on business goals and release timelines
(e.g. Low, Medium, High, Immediate).

2. High-Yield Exam Flashpoints & Key Distinctions

TOP 10 ISTQB CTFL v4.0.1 CHAPTER 5 EXAM TRAPS & DISTRACTORS:

1. "The Test Pyramid states top-layer tests have highest isolation" → FALSE! The top layer (UI/E2E)
has the lowest isolation and slowest execution. Bottom unit tests have the highest isolation.

2. "Usability testing belongs in Quadrant Q4" → FALSE! While performance and security belong in
Q4 (technology-facing), usability testing belongs in Q3 (business-facing, critique product).

3. "Running out of time is never a valid exit criterion" → FALSE! Running out of time or budget IS a
valid exit criterion if stakeholders formally review and accept the residual risk.

4. "Higher priority tests always run before lower priority tests" → FALSE! If a higher-priority test is
dependent on a lower-priority test, the lower-priority test must execute first!

5. "Severity and Priority are identical" → FALSE! Severity is technical impact (system crash); Priority is
business urgency (marketing deadline). A spelling error on the homepage has low severity but high
priority!

6. "Three-point estimation uses simple unweighted average" → FALSE! It uses a weighted
arithmetic mean: E = (a + 4m + b) / 6.

7. "All anomalies reported in testing are defects" → FALSE! Anomalies can turn out to be false-
positives, duplicate reports, or change requests.

8. "Project risks and product risks are managed identically" → FALSE! Project risks threaten
schedule/budget; product risks threaten user quality characteristics.

9. "Test Progress Reports occur only once at the end of testing" → FALSE! Progress reports occur
regularly during testing; Test Completion Reports occur once at milestones.

10. "Test strategy is an examinable section in Chapter 5" → FALSE! The detailed test strategy section
was removed from Foundation Level v4.0 (retained only as a keyword).

4. Realistic ISTQB Practice Exam Questions & Detailed Rationales (Part 1)

Question 1 [K3 - FL-5.1.4]: Using the Three-Point Estimation technique, experts provide the
following test execution estimates: Most Optimistic (a) = 10 hours, Most Likely (m) = 16 hours,
and Most Pessimistic (b) = 34 hours. What are the final weighted Estimate (E) and Standard
Deviation (SD)?

A) E = 18 hours, SD = 4 hours

B) E = 20 hours, SD = 4 hours

C) E = 18 hours, SD = 6 hours

D) E = 16 hours, SD = 2 hours

Correct Answer: A

Rationale: Using PERT formulas:

• E = (a + 4m + b) / 6 = (10 + 4(16) + 34) / 6 = (10 + 64 + 34) / 6 = 108 / 6 = 18 hours

• SD = (b − a) / 6 = (34 − 10) / 6 = 24 / 6 = 4 hours

Thus, the final estimate is 18 ± 4 hours (Section 5.1.4).

Question 2 [K3 - FL-5.1.5]: Test suite execution prioritization is being planned. Test Case TC1 has
High risk priority, but requires prerequisite database records generated by Test Case TC2, which
has Low risk priority. Test Case TC3 has Medium risk priority and is completely independent. In
what order should the tests execute?

A) TC1 → TC3 → TC2

B) TC2 → TC1 → TC3

C) TC3 → TC1 → TC2

D) TC1 → TC2 → TC3

Correct Answer: B

Rationale: Section 5.1.5 states that while priority ordering is desired, test dependencies take
precedence: "If a test case with a higher priority is dependent on a test case with a lower priority, the
lower priority test case must be executed first." Because TC1 depends on TC2, TC2 must run before TC1.
TC3 (Medium) runs after the High-priority workflow completes.

Question 8 [K3 - FL-5.5.1]: A tester discovers that clicking "Print Invoice" causes an unhandled
application crash on iOS devices, though Android devices function normally. Which information
is CRITICAL to include in the defect report to ensure developers can reproduce and fix the bug?
